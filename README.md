# Ferry

**Паром для файлов. Перевёз и ушёл.**

Релей больших файлов через собственный сервер: ничего не остаётся на диске,
всё шифруется на устройстве, отправитель отдаёт байт один раз.

[Проектный документ](docs/FERRY_1.md) · [План работ](docs/PLAN.md) · [Протокол](docs/protocol.md) · [Макеты интерфейса](docs/ferry-mockups/)

</div>

## Зачем это

Файл на пять гигабайт отправить некуда. Почта не примет, облако отдаст по
200 КБ/с, торрент — это про публичные раздачи и требует клиента, а P2P-сервисы
упираются в NAT и в аплоад отправителя: сколько бы человек ни качало, каждый
получит его канал, поделённый на всех.

Ferry — не файлообменник и не торрент. Это **паром**: пришёл, перевёз, ушёл, на
берегу ничего не осталось.

| Схема | Что получает каждый из N |
|---|---|
| Чистый P2P | `аплоад отправителя / N` |
| **Ferry** | `min(аплоад отправителя, свой даунлоад)` — независимо от N |

Плата — исходящий трафик сервера. Но именно он у VPS и есть, а у домашнего
отправителя его нет.

## Три обещания

1. **Сервер не хранит ничего.** Ни файла, ни имени файла, ни метаданных на
   диске. В оперативке — идентификатор раздачи, сокеты и скользящее окно
   байтов, которое тут же вытесняется. Перезапуск сервера гасит все раздачи, и
   это нормально.
2. **Шифрование на устройстве.** AES-256-GCM, ключ живёт во фрагменте ссылки и
   на сервер не уходит никогда. Сервер видит шифротекст, размер и количество
   чанков — больше ничего. Даже имя файла лежит внутри зашифрованного манифеста.
3. **Никакой регистрации.** Ни почты, ни телефона, ни логина.

Проверить второе и третье можно, не веря на слово: [`GET /api/health`](docs/protocol.md)
говорит, пишет ли сервер идентификаторы в журнал, а в `Server/` нет ни строчки,
которая обращается к диску за чем-либо, кроме `ferry.conf`.

## Как начать

### Поднять релей

Нужен сервер с белым IP — недорогой VPS подойдёт.

```bash
# 1. Docker (официальный скрипт)
curl -fsSL https://get.docker.com | sudo sh

# 2. Ferry
git clone https://github.com/vi5vi5vi5/Ferry.git
cd Ferry/Server
./tools/update.sh --force
```

Первая сборка занимает несколько минут: собираются сервер на Qt6, общее ядро и
два клиента — под Linux и под Windows. Повторные запуски быстрые: тяжёлые
стадии берутся из кэша docker. Если клиент под Windows не нужен совсем,
`--skip-windows` вырезает эту стадию целиком.

Потом релей отвечает по адресу `https://<ip-вашего-сервера>/`.

Есть домен? Укажите его — сервер сам получит сертификат Let's Encrypt, и ни
браузер, ни клиент больше не будут ругаться:

```bash
./tools/update.sh --force --domain ferry.example.ru --email you@mail.com
```

Домен запоминается: дальше хватает `./tools/update.sh` без флагов.

#### Если на сервере уже что-то живёт

Порты 80 и 443 может занимать другой сервис — например MeetUp. Ferry заметит
это до сборки и скажет, кто их держит. Дальше два пути.

**Встать за чужой nginx — так лучше.** У Ferry будет свой домен, настоящий
сертификат и адрес без номера порта в ссылке:

```bash
# на стороне Ferry: свой прокси не поднимаем, идём в сеть соседа
./tools/update.sh --force --behind-proxy server_default
```

```bash
# на стороне соседа: отдать Ferry его имя
cd ../../MeetUp/Server
mkdir -p proxy/extra
cp ../../Ferry/Server/proxy/ferry.conf.example proxy/extra/ferry.conf
$EDITOR proxy/extra/ferry.conf          # вписать свой домен в server_name
./tools/update.sh --force --extra-domain fferry.ru
```

Сертификат получится один на оба имени, продлевается он тоже один. Имя сети
соседа смотрится через `docker network ls`; у MeetUp это обычно
`server_default`.

**Или жить отдельно, на своих портах.** Быстрее, но сертификат будет
самоподписанный, а порт — в каждой ссылке:

```bash
./tools/update.sh --force --https-port 8443 --http-port 8081
```

Клиентам тогда понадобится `--insecure` — установщики пропишут это сами.

> **Про соседство есть одна тонкость, которую стоит знать.** У Ferry в
> `docker-compose.yml` имя проекта задано явно (`name: ferry`). Без этого
> compose взял бы его от каталога — `Server`, ровно как у MeetUp, — и
> `docker compose up` в Ferry счёл бы контейнеры MeetUp своими и заменил бы
> их. Если у вас на сервере уже крутится что-то, поднятое из каталога с тем
> же именем, проверьте `docker compose ls` перед первым запуском.

### Поставить клиент

**Клиент раздаёт сам релей.** Не нужно ходить на GitHub за релизами, и версия
клиента по определению совпадает с версией сервера.

**Linux:**

```bash
curl -fsSL https://ferry.example.ru/install.sh | sh
```

**Windows** (PowerShell):

```powershell
irm https://ferry.example.ru/install.ps1 | iex
```

Один файл — в `~/.local/bin` или в `%LOCALAPPDATA%\Programs\ferry`, — адрес
релея прописан в настройках. Ни пакетов, ни служб, ни прав администратора.

Удалить — одной командой, и она знает про себя всё:

```bash
ferry uninstall
```

Сначала показывает список того, что исчезнет — программа, каталог
настроек, запись в PATH пользователя, — и только потом спрашивает. Ferry
ничего не оставляет на диске сверх того, что положил установщик, поэтому
список конечен и его можно показать целиком, а не «мы там что-то
почистили». Недокачки (`*.ferry-part`, `*.ferry-map`) остаются на месте:
это ваши файлы в ваших каталогах, и искать их по всему диску Ferry не
станет — о чём честно предупреждает до вопроса.

Пока у релея нет домена, сертификат самоподписанный, и придётся сказать об этом
прямо:

```bash
curl -fsSLk https://<ip>/install.sh | sh -s -- --insecure
```

```powershell
Add-Type 'using System.Net;public class FerryTls{public static void Ok(){ServicePointManager.ServerCertificateValidationCallback=delegate{return true;};}}'
[FerryTls]::Ok(); $env:FERRY_INSECURE = '1'
irm https://<ip>:8443/install.ps1 | iex
```

Три строки, и именно в таком виде. Привычный однострочник с
`ServerCertificateValidationCallback = { $true }` в Windows PowerShell 5.1
**ломает `Invoke-WebRequest`**: колбэк вызывается из фонового потока, где нет
пространства выполнения PowerShell, падает — и наружу выходит бессмысленное
«Непредвиденная ошибка при передаче». Настоящий делегат .NET этой беды лишён.

### Перевезти

```bash
ferry send дамп.sql.zst
```

Команда заведёт раздачу и сразу напечатает ссылку и QR. Дальше она живёт
источником и показывает, кто и насколько выкачал.

Хеши тома считаются в фоне и уходят получателям по мере подсчёта, а
раздача начинается с первого посчитанного куска. Архив на сто гигабайт не
держит у полосы «считаю хеши», даже если лежит на медленном диске. Со
старым релеем, который так не умеет, всё как раньше: сначала хеши, потом
ссылка.

**Папку тоже целиком:**

```bash
ferry send ~/проект
```

Папка едет как один том — конкатенация файлов в порядке описи, без
выравнивания и заголовков между ними. Сервер об этом не знает вовсе: он
по-прежнему видит линейный поток чанков и одинаково возит и один файл, и
сорок тысяч. У получателя дерево воссоздаётся целиком, с пустыми папками
и пустыми файлами, а имена проверяются заново — путь из описи, который
пытается вылезти за корень, отвергает весь том, а не «чинится» молча.

Симлинки и соединения не возим: разыменовать — значит утащить полдиска
или уйти в цикл, а перенести как есть некуда. Не возим и то, что вообще не
файл: FIFO, сокеты, устройства. Пропущенное перечисляется вслух и ДО
ссылки — чтобы можно было передумать.

А вот файлы OneDrive, которые «только в облаке», возим как обычные:
в Windows они тоже точки переразбора, но считать их ссылками значило бы
отправить человеку пустую папку. Первое чтение подтянет их из облака,
ровно как при обычном копировании в проводнике.

```bash
ferry get "https://ferry.example.ru/t/xxx#yyy"
```

**Ссылку передавайте целиком, вместе с частью после решётки: это и есть ключ.**
Кто получил ссылку — получил том. В кавычках — иначе шелл съест всё после
решётки, то есть ровно ключ.

Раздача живёт, пока запущена `ferry send`. На сервере, куда вы ходите по ssh,
её стоит запускать в `tmux new -s ferry`.

Полезные ключи: `--uses 1` — одноразовая ссылка, `--ttl 1h` — срок жизни,
`--max-concurrent 3` — потолок одновременных получателей.

## Если что-то пошло не так

**Соседний сервис перестал отвечать после запуска Ferry.** Так выглядел
конфликт имён проектов compose: до появления `name: ferry` оба брали имя от
каталога `Server`, и Ferry подменял собой контейнеры соседа. Обновите Ferry и
верните соседа на место — тома с сертификатами привязаны к имени проекта и
никуда не делись:

```bash
cd ~/MeetUp/Server && ./tools/update.sh --force
```

`./tools/update.sh` в Ferry теперь сам замечает такие контейнеры и отказывается
работать, пока они живы.

**Сборка долго висит на OpenSSL.** Это стадия клиента под Windows, она
собирается один раз и дальше берётся из кэша. Совсем не нужна —
`./tools/update.sh --force --skip-windows`.

**Клиент не может соединиться с релеем.** Проверьте, что адрес в настройках
совпадает с тем, по которому релей реально отвечает, включая порт:
`ferry config` показывает, что прописано, `curl -k https://<адрес>/api/health` —
что отвечает.

**`ferry` под Windows ругается на сертификат, а браузер — нет.** Так вели
себя клиенты, собранные до появления доступа к системному хранилищу:
статический OpenSSL искал корни по пути, который существует только внутри
сборочного образа, и не находил ни одного — а значит, не принимал ни одного
сертификата, включая настоящий. Лечится обновлением клиента:

```powershell
irm https://ferry.example.ru/install.ps1 | iex
```

Заодно это уберёт из настроек `insecure = true`, если он остался с тех пор,
когда релей был доступен по IP: установщик переписывает файл целиком.

**Приём идёт в сотни раз медленнее отдачи.** Тот же случай — старый клиент.
Он забирал из сокета по 16 КиБ за оборот цикла и на каждые 16 КиБ
перерисовывал панель, а запись в консоль Windows стоит дорого. Отдачу это
не задевало совсем, поэтому со стороны выглядело как «сервер медленно
раздаёт». Обновление клиента возвращает скорость; проверить можно, направив
вывод в файл — если там быстро, а в консоли медленно, клиент точно старый.

## Из чего это сделано

**Ядро** — [`core/`](core/)
Чистый C++20 без зависимостей: чанкование, манифест, ссылка, BLAKE3, JSON.
Отдельно `ferry-crypto` — HKDF, AES-256-GCM на OpenSSL. Разделение не
косметическое: **серверу криптография не нужна вообще**, он никогда ничего не
расшифровывает, и в его бинаре OpenSSL нет.

**Сервер** — [`Server/`](Server/)
C++20 и Qt6 (Core, Network, WebSockets). Держит скользящее окно чанков в
оперативке и раздаёт их получателям, не заглядывая внутрь. Базы нет
сознательно. Разворачивается через Docker; HTTPS и сертификаты берёт на себя
nginx-прокси.

**Клиент** — [`Cli/`](Cli/)
Один бинарь: C++20, свой мини-клиент WebSocket, статически влинкованный
OpenSSL. Qt здесь нет намеренно — клиент должен ставиться одним файлом на
машину, куда человек зашёл по ssh.

Linux и Windows собираются из одних и тех же исходников; всё, чем системы
отличаются, лежит в [`Cli/platform/`](Cli/platform/) — сокеты, файлы по
смещению, консоль и юникод в путях. Windows-сборка делается тем же образом,
что и серверная, кросс-компилятором MinGW-w64, поэтому Visual Studio для неё
не нужна ни на одной машине.

**Веб-клиент** — пока только [макеты](docs/ferry-mockups/). Приём прямо в
браузере — следующий милестон.

## Что уже работает и чего пока нет

Работает: перевоз файла или папки любого размера с проверкой целостности
по BLAKE3, **ссылка сразу, без ожидания подсчёта хешей**, несколько
получателей одновременно, **позднее подключение с догоном
от других получателей**, докачка после обрыва, одноразовые ссылки, срок
жизни, лимит получателей, доказательство владения ключом (превью-бот
мессенджера не сжигает использование).

Отправитель при этом отдаёт том **один раз**, сколько бы ни было
получателей: опоздавшие берут начало у тех, кто уже скачал, а не у него.
В итоге `ferry send` это видно строкой «повторно: ничего».

Клиент есть под Linux и под Windows: имена файлов кириллицей, пробелы в путях
и `D:\` работают одинаково.

Пока нет:

- **приёма в браузере** — на обоих концах нужен `ferry`;
- **делегирования** — раздача живёт, пока запущен `ferry send`.

Подробности и порядок — в [`docs/PLAN.md`](docs/PLAN.md).

## Разработчикам

Все протоколы описаны в [`docs/protocol.md`](docs/protocol.md) — по ним можно
написать свой клиент. Проверить, что ядро не разошлось с эталоном:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/tests/ferry-core-test
```

Самотесты гоняются и внутри сборки образа: если BLAKE3 или AEAD разойдутся с
официальными векторами, образ просто не соберётся.

Сценарные проверки (реальный перевоз, веер, докачка, отказы):

```bash
./tests/scenarios.sh                 # Linux
```

```powershell
.\tests\scenarios-windows.ps1        # Windows, включая кириллицу в именах
```

```bash
./tests/shared-proxy.sh              # Ferry за чужим nginx рядом с MeetUp
```
