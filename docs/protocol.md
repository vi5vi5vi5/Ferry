# Протокол Ferry, версия 1

Что реально реализовано на сегодня. Проектный документ (§8 в [`FERRY_1.md`](FERRY_1.md))
описывает протокол целиком, включая то, что приедет в следующих милестонах;
здесь — рабочее состояние, по которому можно написать свой клиент.

Отличия от §8 собраны в конце отдельным разделом, чтобы их было видно сразу.

## 1. Что во что превращается

```
файл  ──┬─► чанки по 256 КиБ / 1 МиБ / 4 МиБ (по размеру тома)
        │     └─► BLAKE3 каждого ──► список хешей ──► root = BLAKE3(список)
        │     └─► AES-256-GCM ──► то, что уезжает на сервер
        └─► манифест {имя, размер, root} ──► AES-256-GCM ключом K_meta

ключ K (32 случайных байта) ──┬─► K_data     шифрование чанков
                              ├─► K_meta     шифрование манифеста и списка
                              └─► V          отдаётся серверу, обратно не выводится
```

Размер чанка: `< 64 МиБ → 256 КиБ`, `64 МиБ … 4 ГиБ → 1 МиБ`, `> 4 ГиБ → 4 МиБ`.

**Папка — тот же том.** При `kind: "tree"` том — это конкатенация файлов
в порядке описи, без выравнивания и без заголовков между ними (§3).
Чанки, окно, курсоры и обе волны от этого не меняются ничем: **сервер
не знает, один там файл или сорок тысяч**, и знать не может — опись лежит
внутри зашифрованного манифеста.

Пути в описи — относительные POSIX-пути, отсортированные лексикографически.
Получатель **заново проверяет каждый** и отклоняет том целиком при первом
нарушении, а не «чинит» путь молча: тихо исправленный путь означает, что
файл лёг не туда, куда указано, а хеши при этом сойдутся.
Количество чанков сервер пересчитывает сам и не верит клиенту на слово.

### Вывод ключей

```
K_data = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/data",     L=32)
K_meta = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/meta",     L=32)
V      = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/verifier", L=32)
```

Пустая соль — блок из 32 нулей, как требует RFC 5869.

### Шифрование

AES-256-GCM, тег 16 байт приклеен в конец шифротекста.

```
nonce = [ nonce_prefix : 4 ][ index : 8, big-endian ]
AAD   = [ version : 1 ][ index : 8 BE ][ total_chunks : 8 BE ]
```

`index` в AAD закрывает перестановку чанков, `total_chunks` — обрезание тома.
`nonce_prefix` — 4 случайных байта на раздачу; повтор nonce невозможен, потому
что индекс уникален внутри тома, а префикс — между томами.

Манифест и список хешей шифруются тем же способом ключом `K_meta` с
«индексами» `2^64-1` и `2^64-2`. Пересечься с настоящим чанком они не могут.

**Следствие, о котором стоит знать:** `total_chunks` входит в AAD и для
манифеста тоже. Если сервер соврёт о количестве чанков, манифест не
расшифруется — получатель узнает об этом сразу, а не на середине тома.

### Ссылка

```
https://ferry.example.ru/t/<id>#<key>
                           │      └── 32 байта base64url без выравнивания (43 символа)
                           └───────── 16 байт base64url (22 символа)
```

Фрагмент не попадает ни в HTTP-запрос, ни в логи, ни в `Referer`.

## 2. HTTP

Все тела — JSON. Ошибка выглядит как `{"error": "<код>"}`.

### `POST /api/transfers`

Заводит пустую раздачу. Живёт 60 секунд: столько есть у отправителя, чтобы
дойти до WebSocket и прислать `offer`.

```jsonc
// 201
{ "id": "<22 символа>", "owner_token": "<43 символа>", "public_url": "https://…" }
```

`public_url` — каким адресом релей представляется снаружи (`server.public_url`
в конфиге). Пусто — клиент строит ссылку от адреса, по которому пришёл сам.

Отказы: `server_busy` — упёрлись в потолок раздач или в лимит по адресу.

### `GET /api/transfers/<id>`

```jsonc
// 200
{ "id": "…", "total": 5368709120, "chunk_size": 4194304, "chunks": 1280,
  "manifest": "<b64url шифротекст>", "hash_list": "<b64url шифротекст>",
  "nonce_prefix": "<b64url, 4 байта>", "mode": "key",
  "state": "active" | "closed", "receivers": 2, "uses_left": 3,
  "expires_in_ms": 86397911, "require_approval": false }
```

**Эта ручка ничего не сжигает** — ни использования, ни challenge. По ней ходят
превью-боты мессенджеров, и это в порядке вещей: имени файла здесь нет, оно
внутри зашифрованного манифеста.

Отказы: `transfer_not_found` (в том числе для черновика, до `offer`).

### `GET /api/transfers/<id>/challenge`

```jsonc
// 200
{ "challenge": "<b64url, 16 байт>" }
```

Challenge одноразовый и живёт две минуты.

### `GET /api/health`

Состояние релея и его настройки. Здесь же — проверяемые обещания:
`stores_on_disk: false` и `keeps_identifiers` (пишет ли сервер идентификаторы
раздач в журнал).

### `GET /install.sh`, `GET /install.ps1`, `GET /dl/*`

Установщики клиента и сами бинари. Установщики отдаются не как есть: сервер
подставляет в них адрес, по которому пришёл запрос, — поэтому после
установки клиент знает свой релей и работает без флагов.

`/dl/SHA256SUMS` содержит суммы всех сборок; оба установщика сверяют по нему
то, что скачали, и отказываются ставить несошедшееся.

Заголовок `Content-Type` у `.ps1` обязан нести `charset=utf-8`: `irm … | iex`
декодирует ответ ровно по нему, и без этого PowerShell 5.1 прочитает
кириллицу в кодировке системы.

## 3. WebSocket `/wsf`

**Тот же порт, что и HTTP.** Сервер сам опознаёт запрос на смену протокола и
передаёт сокет вебсокету, поэтому наружу у релея торчит один порт, а не два.

Текстовые сообщения — JSON-управление, бинарные — чанки.

```
бинарный фрейм:  [ op : 1 ][ chunk_index : 8 BE ][ шифротекст + тег GCM ]
op: 1 = CHUNK
```

### Отправитель → сервер

```jsonc
{ "type": "offer", "id": "…", "owner_token": "…",
  "total": 5368709120, "chunk_size": 4194304, "chunks": 1280,
  "nonce_prefix": "<b64url>", "verifier": "<b64url V>",
  "manifest": "<b64url>", "hash_list": "<b64url>",
  "mode": "key",
  "policy": { "uses": 3, "ttl_ms": 3600000, "max_concurrent": 4 } }
```

`policy` целиком необязателен, как и каждое его поле. `uses` отсутствует или
`null` — без лимита.

Сервер проверяет `owner_token` сравнением постоянного времени и пересчитывает
`chunks` из `total` и `chunk_size`. Длина `hash_list` обязана быть ровно
`chunks × 32 + 16` — иначе получатель не смог бы проверить ни одного чанка, а
узнал бы об этом, выкачав половину тома.

Дальше отправитель шлёт бинарные фреймы только из того, что попросил
сервер, и внутри каждой полосы — по возрастанию индекса.

**Просить можно назад.** До M2 отправитель держал один монотонный
курсор и на просьбу о уже отданном чанке не отвечал вообще — молча и
навсегда. Теперь он держит множество чанков, и повторный `need` на старый
диапазон честно приводит к повторной отдаче. Сторожевой таймер сервера
благодаря этому работает на весь том, а не только на его неотправленный
хвост.

`lane` говорит, к какой из двух очередей относится просьба:

| `lane` | Смысл |
|---|---|
| `live` (по умолчанию) | живая волна — то, что уедет всем сразу |
| `backfill` | догон опоздавшего |

Отправитель **выбирает живую волну до конца и только потом берётся за
догон**: иначе один опоздавший тянул бы начало тома впереди всех, кто
качает вовремя. Поле необязательное: релей M1 о нём не знает, а всё,
что он просит, — это живая волна по определению. Сегодня сервер `backfill`
не просит ни разу — это M2.1.

### Получатель → сервер

```jsonc
{ "type": "hello", "id": "…",
  "challenge": "<b64url, тот самый>", "proof": "<b64url HMAC-SHA256(V, challenge)>",
  "name": "Костя",             // необязательно, видит только отправитель
  "have_upto": 512,            // необязательно: докачка, форма M1
  "have": [[0, 511]],          // то же самое диапазонами
  "features": ["ranges"] }     // что этот клиент умеет

{ "type": "have",    "ranges": [[0, 640]] }
{ "type": "request", "ranges": [[641, 1279]], "budget_bytes": 33554432 }
{ "type": "ack",     "upto": 640 }
{ "type": "bad_chunk", "index": 57, "reason": "hash" }
{ "type": "bye" }
```

Бинарные фреймы от получателя — это ответ на `serve`, тот же формат,
что и у отправителя.

**Границы диапазонов включительные с обеих сторон:** `[5,5]` — это ровно
один чанк. Сервер проверяет каждый диапазон целиком и отвечает
`bad_message` на перевёрнутый, дробный или выходящий за пределы тома;
список длиннее 4096 диапазонов тоже отвергается.

`have_upto` и `have` не противоречат друг другу, а **объединяются**:
недокачка, начатая старым клиентом, продолжается новым без единого
лишнего чанка. Курсор живого потока ставится на конец непрерывного
начала, а не на количество принятого: чанк за дыркой живому потоку
не помогает.

`have` только **добавляет**. Получатель не может «разыметь» чанк:
снятие битов по его слову означало бы, что чужое сообщение способно
заставить сервер пересылать уже доставленное сколько угодно раз.

`ack` — тот же `have`, сжатый до одного числа. Клиент шлёт либо одно,
либо другое, а не оба: если сервер объявил `ranges` — `have`, иначе `ack`.

`request` ограничивает то, что сервер будет доставать для этого получателя
второй волной. Не прислал вовсе — считается, что нужен весь том.

### Сервер → клиентам

```jsonc
{ "type": "offer_ok", "chunks": 1280, "features": ["ranges"] }
{ "type": "hello_ok", "receiver_id": 7, "state": "active", "can_seed": false,
  "chunks": 1280, "uses_left": 2, "from_chunk": 512, "features": ["ranges"] }

{ "type": "need", "ranges": [[0, 254]], "budget_bytes": 1069547520,
  "lane": "live" }                                                     // отправителю
{ "type": "peers", "receivers": [ { "id": 7, "name": "Костя",
      "progress": 0.42, "role": "leech" | "catching" | "seed" } ] }    // отправителю
{ "type": "error", "reason": "<код>" }
{ "type": "stats", "src": { "window": 0.04, "peers": 0.96, "sender": 0.0 } }  // получателю
```

### Сидирование и испорченные чанки

`serve` просит получателя отдать чанки обратно. Клиент читает их из
собственной недокачки и **шифрует заново**. Шифротекст получается
**байт в байт тот же**, что прислал отправитель: AES-256-GCM детерминирован,
а ключ, nonce (`prefix ‖ index`) и AAD у обоих одинаковы. Повторный nonce здесь
не ослабление: катастрофа GCM — это один nonce на два РАЗНЫХ открытых
текста, а здесь текст тот же самый.

Следствие, ради которого всё так устроено: **сид не хранит шифротекст**.
Ему достаточно своего файла, и сидирование не стоит ни байта сверх.

`ferry get --seed` не выходит после приёма, а остаётся источником до
Ctrl-C. Файл при этом уже переименован и лежит на месте: ждать окончания
сидирования, чтобы его открыть, не надо.

Завершив приём, клиент **обязательно шлёт последний `have`**. Отчёты идут
не чаще раза в 300 мс, а небольшой том на быстром канале уезжает быстрее —
сервер тогда не услышит ни одного и останется в убеждении, что у
получателя ничего нет. Для приёма это безразлично, а сидировать его
после этого не позовут никогда.

`bad_chunk` — чанк не сошёлся со списком хешей (`reason`: `hash`, `aead`
или `length`). **Это больше не валит передачу.** Пока источник был один и
доверенный, обрыв был честной реакцией; как только чанк может приехать
от другого получателя, она означала бы право любого участника убить
чужую загрузку одним испорченным байтом. Теперь чанк выбрасывается,
сервер забывает, что этот индекс ехал, и просит его заново. Подряд
идущих отказов клиент терпит 64 — дальше чинить нечего, и он сдаётся
вслух.

Сервер проверить, кто прав, не может — ключа он не знает и не должен. Зато
может считать: источник, на который пожаловались **три раза**, больше не
спрашивается в этой раздаче. Отключать его при этом нельзя: жалоба могла
быть и ложной, а его собственная загрузка ни в чём не провинилась.
У отправителя счётчика нет сознательно: отказаться от него значило бы
остаться вовсе без источника.

### Две волны

Получатель, пришедший позже других, больше не получает `no_source`. Сервер
сразу подписывает его на живой поток — хвост и так летит всем и не стоит
ни одного обращения к источнику, — а пропущенное начало тянется второй
волной из двух источников:

1. **из окна**, если чанк ещё там — бесплатно;
2. **от другого получателя** — `serve` самому свободному из тех, у кого
   этот чанк есть. Стоит его простаивающего аплоада и трафика сервера.
   **Отправителю — ноль**;
3. **от отправителя**, полосой `backfill`, — последний рубеж, когда ни у
   кого из группы нужного нет.

Потолок — четыре чанка в пути на раздачу, независимо от источника.

Бинарный фрейм от получателя принимается **только тогда, когда сервер сам
попросил именно его и именно этот индекс**; всё остальное — `bad_message`.
Без этого любой подключившийся мог бы подмешивать байты в чужую раздачу:
получатель мусор отвергнет, но трафик и время были бы потрачены чужие.

Чанк второй волны **не ложится в окно**: он уезжает сразу всем, кто
его ждёт, и забывается. Положи его в окно — догон опоздавшего выталкивал
бы оттуда тех, кто идёт вовремя, и они тоже становились бы опоздавшими.
Оттуда же и маленький потолок: всё, что попрошено, обязано уехать сразу.

Коалесцирование получается само собой: чанк, нужный двоим, попадает в
множество «в пути» один раз и спрашивается у источника один раз.

**Вторая волна работает только с клиентом, объявившим `ranges`.** Она
держится на том, что получатель говорит, что у него есть; клиент M1
этого не умеет, и для него `no_source` остаётся — что честнее, чем отдать
том с дырой молча.

`stats` говорит получателю, откуда приехало то, что у него есть, — долями
от числа чанков. Сам он этого знать не может: фрейм из окна и фрейм от
пира одинаковы до байта — и это не недоработка, а та самая причина, по
которой веер на сервере не копирует полезную нагрузку. Приходит не
чаще четырёх раз в секунду.

В §8 у `stats` есть ещё `rate_bps` и `eta_ms` — их здесь нет сознательно:
скорость и остаток получатель считает сам и точнее — по своему каналу, а
не по тому, что ушло в сокет на сервере.

Ролей в `peers` три, а не две: к `leech` и `seed` добавился **`catching`** — тот,
кто тянет начало второй волной. По процентам он выглядит отстающим,
хотя на самом деле просто пришёл позже.

`can_seed` говорит, будут ли этого получателя просить отдавать: `true`, если он
сам объявил `backfill`.

### Как стороны догавариваются о возможностях

Оба конца объявляют `features`: клиент в `hello`, сервер в `hello_ok` и
`offer_ok`. Сегодня имён два:

| Имя | Что означает |
|---|---|
| `ranges` | говорит `have` и `request` диапазонами |
| `backfill` | умеет отвечать на `serve` и рассылать его |

Зачем это нужно. Неизвестное **сообщение** здесь — это `bad_message`, а не
«промолчу». Строгость правильная — мусор на проводе обязан быть виден
сразу, — но за неё приходится платить честным ответом на вопрос «а ты
меня поймёшь». Без этого новый клиент, встретив старый релей, получил бы
отказ на первом же `have`.

Неизвестные **поля** внутри сообщения, наоборот, игнорируются молча —
поэтому `have` и `features` безопасно лежат внутри `hello`, который
посылается до того, как сервер успел что-либо о себе сказать. Точно так же
сервер молча пропускает незнакомые имена в `features`: клиент из будущего
объявит что-то новое, и это не должно ссорить его с сегодняшним релеем.

### Порядок разговора

```
отправитель                     сервер                      получатель
    │  POST /api/transfers        │                              │
    │ ◄─── id, owner_token ───────┤                              │
    │  WS: offer ────────────────►│                              │
    │ ◄─── offer_ok ──────────────┤                              │
    │ ◄─── need [0,254] ──────────┤                              │
    │  CHUNK 0..254 ─────────────►│ (копятся в окне)             │
    │                             │ ◄── GET /api/transfers/<id> ─┤
    │                             │ ◄── GET …/challenge ─────────┤
    │                             │ ◄── WS: hello + proof ───────┤
    │                             ├──── hello_ok ───────────────►│
    │                             ├──── CHUNK 0.. ──────────────►│
    │ ◄─── need [255,…] ──────────┤ ◄── ack ─────────────────────┤
```

## 4. Кредит, окно и обратное давление

Отправитель не льёт сколько влезет — сервер просит. Правило одно:

```
попросить можно до:  min(всего_чанков, самый_медленный_курсор + вместимость_окна)
```

Вместимость окна считается в **фреймах**, а не в открытых чанках: в окне лежит
ровно то, что приехало и уедет дальше, вместе с заголовком и тегом GCM.

Получателю сервер шлёт, пока в буфере его сокета меньше 4 МиБ. Быстрый едет
быстро, медленный медленно, друг с другом они не связаны.

Если попрошенное не едет дольше пяти секунд, сервер просит заново: весь поток
держится на одном сообщении `need`, и потерянное сообщение иначе означало бы
раздачу, которая тихо стоит навсегда.

| Код | Когда |
|---|---|
| `need_key` | ключ не предъявлен или не сошёлся. **Использование НЕ списано** |
| `transfer_not_found` | нет такой раздачи (или это ещё черновик) |
| `uses_exhausted` | лимит использований исчерпан |
| `expired` | вышел срок жизни |
| `too_many_receivers` | превышен `max_concurrent` |
| `sender_gone` | отправитель отключился |
| `no_source` | начало тома отдать неоткуда: раздача ушла дальше окна |
| `chunk_mismatch` | чанк не сошёлся со списком хешей (проверка на стороне клиента) |
| `server_busy` | кончилась память под окна или упёрлись в лимиты |
| `owner_conflict` | `owner_token` не подошёл или раздача уже занята |
| `bad_message` | сообщение не разобралось или нарушает протокол |

**Порядок проверок при `hello` важен и является частью протокола:** сначала
challenge и доказательство владения ключом, и только потом политика. Иначе
превью-бот мессенджера, дёрнувший ссылку без фрагмента, сжигал бы одноразовую
раздачу раньше человека.

## 6. Чем это отличается от §8 проектного документа

Осознанные расхождения — их три, и все в сторону работоспособности.

1. **`hello` несёт challenge обратно.** В §8 получатель шлёт только `proof`, и
   сервер должен как-то помнить, какой challenge кому выдал. Challenge выдаётся
   по HTTP, а предъявляется по WebSocket — это разные соединения, связать их
   нечем. Поэтому получатель возвращает challenge вместе с ответом, а сервер
   держит выданные значения в оперативке две минуты и гасит после первого
   использования.

2. **`features` в `hello`, `hello_ok` и `offer_ok`.** В §8 их нет: там протокол
   описан целиком и сразу, а реально он приезжает милестонами, и клиент
   с сервером вполне могут оказаться разных возрастов. Подробно — выше.

3. **Один порт вместо двух.** §8 подразумевает отдельный порт для WebSocket
   (как в MeetUp). Сервер Ferry принимает смену протокола на том же порту,
   что и HTTP: клиенту достаточно знать адрес, а nginx всё равно сводит всё
   на 443.

Ещё не реализовано из §8 и приедет позже:

| Что | Когда |
|---|---|
| `flow` — делёж канала получателя между двумя волнами | позже, когда понадобится |
| `approve` / `policy` / `revoke` / `resume_owner`, делегирование | M4 |
| парольный режим с Argon2id | M4 |

`subscribe_live` отдельным шагом так и не нужен: подписка происходит сразу
при `hello`, а само сообщение принимается и игнорируется.

`flow` так и не понадобился, хотя по плану шёл в M2. Он делит канал
получателя между двумя волнами — а делёж получился сам собой из
двух потолков, которые и так нужны: очередь сокета получателя и число
чанков второй волны в пути. Добавим, когда появится случай, в котором
этого не хватает.
