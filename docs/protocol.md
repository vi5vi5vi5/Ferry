# Протокол Ferry, версия 1

Что реально реализовано в M1. Проектный документ (§8 в [`FERRY_1.md`](FERRY_1.md))
описывает протокол целиком, включая то, что приедет в следующих милестонах;
здесь — рабочее состояние, по которому можно написать свой клиент.

Отличия от §8 собраны в конце отдельным разделом, чтобы их было видно сразу.

---

## 1. Что во что превращается

```
файл  ──┬─► чанки по 256 КиБ / 1 МиБ / 4 МиБ (по размеру тома)
        │     └─► BLAKE3 каждого ──► список хешей ──► root = BLAKE3(список)
        │     └─► AES-256-GCM ──► то, что уезжает на сервер
        └─► манифест {имя, размер, root} ──► AES-256-GCM ключом K_meta

ключ K (32 случайных байта) ──┬─► K_data     шифрование чанков
                              ├─► K_meta     шифрование манифеста и списка
                              └─► V          отдаётся серверу, обратно не выводится
```

Размер чанка: `< 64 МиБ → 256 КиБ`, `64 МиБ … 4 ГиБ → 1 МиБ`, `> 4 ГиБ → 4 МиБ`.
Количество чанков сервер пересчитывает сам и не верит клиенту на слово.

### Вывод ключей

```
K_data = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/data",     L=32)
K_meta = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/meta",     L=32)
V      = HKDF-SHA256(ikm=K, salt="", info="ferry/v1/verifier", L=32)
```

Пустая соль — блок из 32 нулей, как требует RFC 5869.

### Шифрование

AES-256-GCM, тег 16 байт приклеен в конец шифротекста.

```
nonce = [ nonce_prefix : 4 ][ index : 8, big-endian ]
AAD   = [ version : 1 ][ index : 8 BE ][ total_chunks : 8 BE ]
```

`index` в AAD закрывает перестановку чанков, `total_chunks` — обрезание тома.
`nonce_prefix` — 4 случайных байта на раздачу; повтор nonce невозможен, потому
что индекс уникален внутри тома, а префикс — между томами.

Манифест и список хешей шифруются тем же способом ключом `K_meta` с
«индексами» `2^64-1` и `2^64-2`. Пересечься с настоящим чанком они не могут.

**Следствие, о котором стоит знать:** `total_chunks` входит в AAD и для
манифеста тоже. Если сервер соврёт о количестве чанков, манифест не
расшифруется — получатель узнает об этом сразу, а не на середине тома.

### Ссылка

```
https://ferry.example.ru/t/<id>#<key>
                           │      └── 32 байта base64url без выравнивания (43 символа)
                           └───────── 16 байт base64url (22 символа)
```

Фрагмент не попадает ни в HTTP-запрос, ни в логи, ни в `Referer`.

## 2. HTTP

Все тела — JSON. Ошибка выглядит как `{"error": "<код>"}`.

### `POST /api/transfers`

Заводит пустую раздачу. Живёт 60 секунд: столько есть у отправителя, чтобы
дойти до WebSocket и прислать `offer`.

```jsonc
// 201
{ "id": "<22 символа>", "owner_token": "<43 символа>", "public_url": "https://…" }
```

`public_url` — каким адресом релей представляется снаружи (`server.public_url`
в конфиге). Пусто — клиент строит ссылку от адреса, по которому пришёл сам.

Отказы: `server_busy` — упёрлись в потолок раздач или в лимит по адресу.

### `GET /api/transfers/<id>`

```jsonc
// 200
{ "id": "…", "total": 5368709120, "chunk_size": 4194304, "chunks": 1280,
  "manifest": "<b64url шифротекст>", "hash_list": "<b64url шифротекст>",
  "nonce_prefix": "<b64url, 4 байта>", "mode": "key",
  "state": "active" | "closed", "receivers": 2, "uses_left": 3,
  "expires_in_ms": 86397911, "require_approval": false }
```

**Эта ручка ничего не сжигает** — ни использования, ни challenge. По ней ходят
превью-боты мессенджеров, и это в порядке вещей: имени файла здесь нет, оно
внутри зашифрованного манифеста.

Отказы: `transfer_not_found` (в том числе для черновика, до `offer`).

### `GET /api/transfers/<id>/challenge`

```jsonc
// 200
{ "challenge": "<b64url, 16 байт>" }
```

Challenge одноразовый и живёт две минуты.

### `GET /api/health`

Состояние релея и его настройки. Здесь же — проверяемые обещания:
`stores_on_disk: false` и `keeps_identifiers` (пишет ли сервер идентификаторы
раздач в журнал).

### `GET /install.sh`, `GET /install.ps1`, `GET /dl/*`

Установщики клиента и сами бинари. Установщики отдаются не как есть: сервер
подставляет в них адрес, по которому пришёл запрос, — поэтому после
установки клиент знает свой релей и работает без флагов.

`/dl/SHA256SUMS` содержит суммы всех сборок; оба установщика сверяют по нему
то, что скачали, и отказываются ставить несошедшееся.

Заголовок `Content-Type` у `.ps1` обязан нести `charset=utf-8`: `irm … | iex`
декодирует ответ ровно по нему, и без этого PowerShell 5.1 прочитает
кириллицу в кодировке системы.

## 3. WebSocket `/wsf`

**Тот же порт, что и HTTP.** Сервер сам опознаёт запрос на смену протокола и
передаёт сокет вебсокету, поэтому наружу у релея торчит один порт, а не два.

Текстовые сообщения — JSON-управление, бинарные — чанки.

```
бинарный фрейм:  [ op : 1 ][ chunk_index : 8 BE ][ шифротекст + тег GCM ]
op: 1 = CHUNK
```

### Отправитель → сервер

```jsonc
{ "type": "offer", "id": "…", "owner_token": "…",
  "total": 5368709120, "chunk_size": 4194304, "chunks": 1280,
  "nonce_prefix": "<b64url>", "verifier": "<b64url V>",
  "manifest": "<b64url>", "hash_list": "<b64url>",
  "mode": "key",
  "policy": { "uses": 3, "ttl_ms": 3600000, "max_concurrent": 4 } }
```

`policy` целиком необязателен, как и каждое его поле. `uses` отсутствует или
`null` — без лимита.

Сервер проверяет `owner_token` сравнением постоянного времени и пересчитывает
`chunks` из `total` и `chunk_size`. Длина `hash_list` обязана быть ровно
`chunks × 32 + 16` — иначе получатель не смог бы проверить ни одного чанка, а
узнал бы об этом, выкачав половину тома.

Дальше отправитель шлёт бинарные фреймы **по порядку**, в пределах того, что
попросил сервер.

### Получатель → сервер

```jsonc
{ "type": "hello", "id": "…",
  "challenge": "<b64url, тот самый>", "proof": "<b64url HMAC-SHA256(V, challenge)>",
  "name": "Костя",        // необязательно, видит только отправитель
  "have_upto": 512 }      // необязательно: докачка

{ "type": "ack", "upto": 640 }
{ "type": "bye" }
```

`have_upto` — сколько чанков подряд с начала у получателя уже есть. Сервер
ставит курсор туда и не присылает то, что и так лежит на диске.

### Сервер → клиентам

```jsonc
{ "type": "offer_ok", "chunks": 1280 }
{ "type": "hello_ok", "receiver_id": 7, "state": "active", "can_seed": false,
  "chunks": 1280, "uses_left": 2, "from_chunk": 512 }

{ "type": "need", "ranges": [[0, 254]], "budget_bytes": 1069547520 }   // отправителю
{ "type": "peers", "receivers": [ { "id": 7, "name": "Костя",
      "progress": 0.42, "role": "leech" | "seed" } ] }                  // отправителю
{ "type": "error", "reason": "<код>" }
```

`can_seed` в M1 всегда `false`: reflected backfill приходит в M2, и врать об
этом нельзя — получатель должен знать, чего от него не ждут.

### Порядок разговора

```
отправитель                     сервер                      получатель
    │  POST /api/transfers        │                              │
    │ ◄─── id, owner_token ───────┤                              │
    │  WS: offer ────────────────►│                              │
    │ ◄─── offer_ok ──────────────┤                              │
    │ ◄─── need [0,254] ──────────┤                              │
    │  CHUNK 0..254 ─────────────►│ (копятся в окне)             │
    │                             │ ◄── GET /api/transfers/<id> ─┤
    │                             │ ◄── GET …/challenge ─────────┤
    │                             │ ◄── WS: hello + proof ───────┤
    │                             ├──── hello_ok ───────────────►│
    │                             ├──── CHUNK 0.. ──────────────►│
    │ ◄─── need [255,…] ──────────┤ ◄── ack ─────────────────────┤
```

## 4. Кредит, окно и обратное давление

Отправитель не льёт сколько влезет — сервер просит. Правило одно:

```
попросить можно до:  min(всего_чанков, самый_медленный_курсор + вместимость_окна)
```

Вместимость окна считается в **фреймах**, а не в открытых чанках: в окне лежит
ровно то, что приехало и уедет дальше, вместе с заголовком и тегом GCM.

Получателю сервер шлёт, пока в буфере его сокета меньше 4 МиБ. Быстрый едет
быстро, медленный медленно, друг с другом они не связаны.

Если попрошенное не едет дольше пяти секунд, сервер просит заново: весь поток
держится на одном сообщении `need`, и потерянное сообщение иначе означало бы
раздачу, которая тихо стоит навсегда.

## 5. Коды ошибок

| Код | Когда |
|---|---|
| `need_key` | ключ не предъявлен или не сошёлся. **Использование НЕ списано** |
| `transfer_not_found` | нет такой раздачи (или это ещё черновик) |
| `uses_exhausted` | лимит использований исчерпан |
| `expired` | вышел срок жизни |
| `too_many_receivers` | превышен `max_concurrent` |
| `sender_gone` | отправитель отключился |
| `no_source` | начало тома отдать неоткуда: раздача ушла дальше окна |
| `chunk_mismatch` | чанк не сошёлся со списком хешей (проверка на стороне клиента) |
| `server_busy` | кончилась память под окна или упёрлись в лимиты |
| `owner_conflict` | `owner_token` не подошёл или раздача уже занята |
| `bad_message` | сообщение не разобралось или нарушает протокол |

**Порядок проверок при `hello` важен и является частью протокола:** сначала
challenge и доказательство владения ключом, и только потом политика. Иначе
превью-бот мессенджера, дёрнувший ссылку без фрагмента, сжигал бы одноразовую
раздачу раньше человека.

## 6. Чем это отличается от §8 проектного документа

Осознанные расхождения — их три, и все в сторону работоспособности.

1. **`hello` несёт challenge обратно.** В §8 получатель шлёт только `proof`, и
   сервер должен как-то помнить, какой challenge кому выдал. Challenge выдаётся
   по HTTP, а предъявляется по WebSocket — это разные соединения, связать их
   нечем. Поэтому получатель возвращает challenge вместе с ответом, а сервер
   держит выданные значения в оперативке две минуты и гасит после первого
   использования.

2. **`have_upto` в `hello`.** В §8 есть полноценные диапазоны `have`, но они
   имеют смысл вместе с backfill, то есть в M2. Пока чанки приходят по порядку,
   префикса достаточно, а формат карты принятого на диске уже заложен под
   произвольные диапазоны.

3. **Один порт вместо двух.** §8 подразумевает отдельный порт для WebSocket
   (как в MeetUp). Сервер Ferry принимает смену протокола на том же порту,
   что и HTTP: клиенту достаточно знать адрес, а nginx всё равно сводит всё
   на 443.

Ещё не реализовано из §8 и приедет позже: `request` / `have` / `serve` и
reflected backfill (M2), `approve` / `policy` / `revoke` / `resume_owner` и
делегирование (M4), парольный режим с Argon2id (M4), `stats` с разбивкой
источников, `subscribe_live` как отдельный шаг (сейчас подписка происходит
сразу при `hello`; сообщение принимается и игнорируется).
