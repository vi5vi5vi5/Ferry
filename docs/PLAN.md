# Ferry · план работ

Рабочий план к [`FERRY_1.md`](FERRY_1.md). Проектный документ отвечает на вопрос
«что строим», этот — на вопрос «в каком порядке и чем это собирать», и фиксирует
три решения, которых в проектном документе нет: **какой клиент делать первым**,
**чем собирать CLI** и **как это ставится у нового человека**.

---

## 1. Короткий итог

| Вопрос | Решение |
|---|---|
| Какой клиент первым | **CLI.** Веб-получатель — третьим милестоном, веб-отправитель — четвёртым. |
| Чем собирать CLI | **Один статический бинарь на C++20 без Qt** (OpenSSL + свой мини-клиент WS). |
| Как ставится сервер | `git clone && ./tools/update.sh --force --domain …` — как в MeetUp, один в один. |
| Как ставится клиент | `curl -fsSL https://<ваш-релей>/install.sh | sh` — **релей раздаёт собственный клиент**. |
| Что такое «прототип» | Милестон M1: файл на 5 ГБ уезжает с серого сервера на белый через релей и сходится по BLAKE3. |

---

## 2. Решение №1 · Сначала CLI, потом веб

Проектный документ (§13, фаза 1) ставит веб-клиент в первый же шаг. Предлагаю
поменять порядок. Аргументы:

**За CLI первым:**

1. **Один язык и один цикл сборки.** `libferry-core` пишется один раз на C++ и
   сразу же используется обоими концами. При веб-первом подходе core пишется
   дважды — на C++ для сервера и на JS для браузера — и расхождение форматов
   ловится отладкой по обе стороны сокета одновременно.
2. **Нет браузерного минного поля.** Путь A (File System Access), путь B (OPFS +
   `createSyncAccessHandle` в воркере), путь C (Service Worker → менеджер
   загрузок), `navigator.storage.estimate()`, срыв фоновых вкладок на мобильных,
   потоковая отдача в Safari (§14 — отмечена как высокий риск) — это недели, и ни
   одна из них не проверяет тезис продукта.
3. **Произвольный доступ к файлу достаётся бесплатно.** `pwrite`/`pread` — это то,
   ради чего в браузере городятся OPFS и FSA. Значит две волны, backfill,
   сидирование и докачка после обрыва в CLI стоят почти ничего, и **ключевой
   тезис (§13, фаза 2: «третий подключился на 60 %, у первых двух скорость не
   изменилась») проверяется на месяцы раньше**.
4. **CLI становится эталонной реализацией протокола.** Когда сядем за веб-клиент,
   на другом конце будет заведомо рабочий собеседник. Это разница между «отлаживаю
   одну сторону» и «отлаживаю две неизвестные стороны через непроверенный протокол».
5. **Это ваш собственный сценарий.** «Передать файл с линукс-сервера, к которому
   подключаюсь по ssh» — браузером не делается вообще.

**Что мы теряем, отложив веб:** обещание «ничего не установлено» временно не
выполняется. Но получатель-в-браузере приходит уже в M3 — то есть в тот момент,
когда под ним есть проверенный сервер и отлаженный протокол.

**Макеты (`docs/ferry-mockups/`) при этом не пропадают.** Они уже разложены на три
слоя, из которых выбрасывается только `ferry.js` + `fixtures.js`. Более того, CLI
сознательно рисует те же сущности — карту тома, роли получателей, две волны, —
поэтому к M3 у нас будет работающая семантика, а не только разметка.

## 3. Решение №2 · CLI — один бинарь без Qt

Проектный документ (§9) выбирает Qt6 для сервера, и это правильно: там уже есть
готовый Docker, nginx с Let's Encrypt и знакомое слоение. Но **для клиента Qt —
плохая цена**: 20+ МБ библиотек на каждой машине, куда мы хотим поставить `ferry`,
и установка перестаёт быть «скачал один файл».

```
Сервер   C++20 + Qt6 (Core, Network, WebSockets)   ← как в MeetUp
Ядро     C++20, без Qt, без зависимостей           ← общее
CLI      C++20 + OpenSSL + свой мини-клиент WS     ← один файл
```

**Что нужно клиенту, чего нет в стандартной библиотеке:**

| Нужно | Чем берём | Объём |
|---|---|---|
| TLS | OpenSSL (`libssl`/`libcrypto`, есть на любой Ubuntu) | линкуем статически |
| WebSocket | свой клиент: HTTP Upgrade + фрейминг + маскирование + ping/pong | ~500 строк, один раз |
| AES-256-GCM, HKDF-SHA256 | OpenSSL EVP | — |
| BLAKE3 | официальная C-реализация, вендорим | 1 папка |
| QR в терминал | `qrcodegen` (Nayuki, MIT), один .c | 1 файл |

Свой WS-клиент — это единственная нетривиальная часть, и она полностью
предсказуема: клиент маскирует фреймы, сервер нет, фрагментацию через nginx
ждать неоткуда (после Upgrade это прозрачный TCP-туннель).

**Что важно знать про сервер: ему криптография не нужна вообще.** Он никогда
ничего не расшифровывает, ему нужны только HMAC-SHA256 для challenge-response и
случайные байты — и то и другое есть в Qt (`QMessageAuthenticationCode`,
`QRandomGenerator::system()`). Значит `Crypto.cpp` из ядра в серверный бинарь
просто не залинкуется, и OpenSSL в рантайм-образе не появится.

**Альтернатива, если решим иначе:** CLI на Qt6, собранный в докере и разложенный
тарболлом вместе с `libQt6*.so` и `rpath=$ORIGIN/lib`. Работает, ставится сложнее,
весит в 15 раз больше. Считаю это запасным вариантом, а не основным.

## 4. Решение №3 · Релей раздаёт собственный клиент

Главное требование — «установка максимально простая для нового пользователя, как
в meetup». В MeetUp это работает, потому что клиент — браузер. У нас клиент нужно
принести на машину. Предлагаю так:

```bash
# на белом сервере — поднять релей (как MeetUp, один в один)
curl -fsSL https://get.docker.com | sudo sh
git clone https://github.com/vi5vi5vi5/Ferry.git
cd Ferry/Server
./tools/update.sh --force --domain ferry.example.ru --email you@mail.com
```

```bash
# на любой машине, откуда надо слать файлы — поставить клиент
curl -fsSL https://ferry.example.ru/install.sh | sh
ferry send ~/backup.tar.zst
```

Как это устроено: **тот же `Dockerfile`, который собирает сервер, отдельной
стадией собирает и Linux-клиент** и кладёт бинарь в веб-корень. Релей отдаёт
`/install.sh`, `/dl/ferry-linux-x86_64` и `/dl/SHA256SUMS`.

Что это даёт:

- нового человека не нужно вести на GitHub Releases — у него уже есть адрес релея;
- версия клиента **по определению** совпадает с версией сервера, протокол не
  разъезжается;
- `install.sh` прописывает адрес релея в `~/.config/ferry/config`, поэтому
  `ferry send file` работает без единого флага;
- нет пайплайна релизов, который пришлось бы поддерживать ради прототипа.

`install.sh` определяет архитектуру, сверяет sha256, ставит в `~/.local/bin`
(или в `/usr/local/bin`, если запущен под sudo) и печатает первую команду.
Если готового бинаря под архитектуру нет — предлагает собрать из исходников
(`apt install build-essential cmake libssl-dev`, полминуты на таком объёме кода).

### Грабли, которые видно заранее: версия glibc

Сервер собирается на `debian:bookworm` (glibc 2.36). Бинарь, собранный там, **не
запустится на Ubuntu 22.04** (glibc 2.35). Поэтому стадия сборки клиента в
`Dockerfile` — отдельная.

Изначально планировался `debian:bullseye` (glibc 2.31, дотянулся бы до
Ubuntu 20.04), но он снят с поддержки: пакеты уехали в `archive.debian.org`,
сборка падает на 404, а статически влинкованный OpenSSL перестал бы получать
исправления. Взят `ubuntu:22.04` — glibc 2.35, поддержка до 2027 года,
покрывает Ubuntu 22.04+ и Debian 12+. OpenSSL линкуем статически, снаружи
остаётся только glibc.

## 6. M1 · Прототип: один отправитель, один получатель

**Критерий приёмки:** файл на 5 ГБ уезжает с серого сервера (за NAT, порты
закрыты) через релей на белом IP на третью машину, приходит целым, BLAKE3
сходится, `Ctrl-C` посреди загрузки и повторный `ferry get` продолжают с того же
места.

### Ядро
- `Chunker`: выбор размера чанка по §3, смещения, количество.
- `Crypto`: HKDF-SHA256 (K_data / K_meta / V), AES-256-GCM с nonce и AAD по §4.
- `HashList`: BLAKE3 по открытым чанкам, `root = BLAKE3(hashes)`.
- `Manifest`: только `kind:"file"` — имя, размер. Дерево — в M5.
- `Link`: генерация 16-байтного id и 32-байтного ключа, base64url, сборка/разбор.

### Сервер
- `TransferRegistry` — id → сессия, уборка по TTL, потолок памяти.
- `TransferSession` — метаданные, курсоры, шифротексты манифеста и списка хешей
  как непрозрачные байты.
- `RingWindow` — кольцевой буфер чанков в RAM, drop-behind.
- HTTP: `POST /api/transfers`, `GET /api/transfers/<id>`, `GET …/challenge`,
  `GET /api/health`, отдача `/install.sh`, `/dl/*` и страницы `/t/<id>`.
- WS `/wsf`: `offer` → `offer_ok`; `hello` + proof → `hello_ok`; `need` с кредитом
  отправителю; бинарные CHUNK; `ack`; `bye`; коды ошибок из §8.
- **Challenge-response на `V` берём сразу**, хотя по §13 он в фазе 3: это ~50
  строк на `QMessageAuthenticationCode`, и без него любой превью-бот мессенджера
  будет жечь раздачу, как только появятся лимиты.
- Pull с кредитом и backpressure по `bytesToWrite()` — тоже сразу: с одним
  получателем это тривиально, но это и есть настоящая архитектура, а не заглушка.

### CLI
```
ferry send <file> [--uses N] [--ttl 24h] [--relay host]
ferry get  "<ссылка>" [-o path]
ferry version
```
- `send`: считает хеши (с прогрессом — на 5 ГБ это секунды, но молчать нельзя),
  создаёт раздачу, печатает ссылку и QR, дальше живёт как источник и показывает
  панель: том, ссылка, получатели, карта тома, скорость.
- `get`: вытягивает метаданные, расшифровывает манифест, показывает что за том и
  спрашивает подтверждение, пишет через `pwrite` рядом с битовой картой
  `.ferry-part`, по завершении сверяет и переименовывает.
- Вывод — цветной в tty, простой при перенаправлении, `NO_COLOR` уважается.

### Инфраструктура
- `Dockerfile` (3 стадии: сервер, клиент-bullseye, рантайм), `docker-compose.yml`,
  `proxy/` — портируются из MeetUp с правками под Ferry (location `/wsf`, длинные
  таймауты, gzip выключен на `/dl/`).
- `tools/update.sh` и `update.ps1` — из MeetUp почти без изменений.

### Чего в M1 нет

Backfill, двух волн, сидирования, делегирования, парольного режима, папок,
веб-клиента.

> Список выше короче, чем планировался. Три вещи из него уехали в M1 раньше
> срока, потому что в однополучательском виде стоили почти ничего, а
> переделывать их потом пришлось бы целиком: **несколько получателей
> одновременно** (свой курсор и своё обратное давление на каждого),
> **политика `uses` / `ttl` / `max_concurrent`** и **доказательство владения
> ключом**. Windows-клиент вошёл отдельным милестоном M1.5.

## 7. Дальше

| Милестон | Содержание | Критерий |
|---|---|---|
| **M2 · Веер и две волны** | `have`/`request`/`serve`/`flow`, backfill из окна и от отправителя (M2.1), reflected backfill от получателей и коалесцирование (M2.2), эвристика «догон vs две волны», карта тома в CLI по-настоящему | Трое качают, третий подключается на 60 %, у первых двух скорость не меняется, **а отправитель отдаёт том ровно один раз**. Расписано ниже отдельным разделом. |
| **M3 · Веб-получатель** | Экраны R1, R2, R3, R5 и ошибки из макетов; путь A (Chrome, FSA) и путь C (Service Worker); WebCrypto-зеркало ядра | Друг открывает ссылку в браузере на телефоне и качает то, что я отправил с сервера командой `ferry send`. |
| **M4 · Политика и веб-отправитель** | Подтверждение приёма, `leave_open`/`on_owner_leave`, делегирование на сид, `resume_owner`, парольный режим с Argon2id; экраны S1–S5 | Отправитель закрыл вкладку, раздача живёт на сиде, счётчик верен. |
| **M5 · Папки** — **сделано в CLI** | Манифест-дерево, том как конкатенация, санитизация путей, приём деревом. ZIP store — вместе с веб-клиентом в M3 | Папка приезжает деревом, `diff -r` молчит. |

Из M2 уже есть **несколько получателей одновременно** с отдельным курсором и
обратным давлением на каждого; из M4 — **`uses`, TTL, `max_concurrent`** и
`owner_token` как удостоверение отправителя.

### M1.5 · Клиент под Windows — сделано

Вклинилось между M1 и M2 по прямому запросу: рабочая станция на Windows,
и файлы надо возить в обе стороны каждый день.

**Результат:** `irm https://<релей>/install.ps1 | iex` ставит `ferry.exe`
одной командой. Проверено на настоящей Windows 11: том с кириллицей в имени
и пробелами в пути уезжает на линукс-сервер и обратно, обрыв и докачка
работают, отказы объясняются словами. Сценарии — в
[`tests/scenarios-windows.ps1`](../tests/scenarios-windows.ps1).

Что всплыло по дороге и чего не было видно из плана:

- **`Invoke-WebRequest` в PowerShell 5.1 отдаёт тело байтами, а не строкой.**
  Из-за этого сверка sha256 в установщике молча не выполнялась: `$bytes -split`
  разваливал массив на отдельные числа, нужная строка не находилась, и
  проверка тихо пропускалась. Теперь тело декодируется явно, а пропуск
  сверки — это громкое предупреждение, а не тишина.
- **`.ps1` без BOM на Windows PowerShell 5.1 читается в кодировке системы**,
  и кириллица в нём умирает ещё до разбора. Поэтому `scenarios-windows.ps1`
  лежит с BOM, а `install.ps1` — наоборот без BOM: его читает `irm | iex`
  по заголовку `charset=utf-8`, и лишний U+FEFF попал бы прямо в `iex`.
- **`Start-Process -ArgumentList` не кавычит аргументы** — путь с пробелом
  доезжает до программы обрубленным. Это беда вызывающего, а не клиента, но
  в тестах на неё натыкаешься первым делом.
- **Карта принятого писалась раз в две секунды.** На быстром канале это до
  двухсот мегабайт работы, теряемых при жёстком убийстве процесса, а обрыв
  в первые секунды вообще оставлял недокачку без карты. Теперь карта пишется
  сразу при создании файла и дальше раз в полсекунды: она весит сотни байт,
  экономить на ней было не на чем.

Ниже — то, что планировалось и подтвердилось.

Тот же `ferry`, собранный кросс-компилятором MinGW-w64 в том же образе, что и
релей. Раздаётся тем же способом: `irm https://<релей>/install.ps1 | iex`.
Visual Studio и vcpkg на рабочей станции не нужны.

Четыре места, где Windows отличается не косметически:

1. **Сокеты** — Winsock вместо `poll`/`fcntl`. Ожидание готовности через
   `select`, а НЕ через `WSAPoll`: у последнего известный баг — он не сигналит
   об ошибке неудачного `connect`, и клиент повисал бы на мёртвом адресе.
2. **Юникод в путях** — `GetCommandLineW` вместо `argv`, `CreateFileW` вместо
   `open`. Без этого имя файла кириллицей превращается в мусор, а у нас имена
   кириллицей.
3. **Файловый доступ** — `pread`/`pwrite` на Windows нет; нужен свой слой.
4. **Консоль** — `SetConsoleMode(ENABLE_VIRTUAL_TERMINAL_PROCESSING)` и
   `SetConsoleOutputCP(CP_UTF8)`, иначе рамки и карта тома превращаются в кашу.
   Старый `conhost` не умеет — падаем в простой режим.

Криптография остаётся **одна на все платформы**: тот же OpenSSL, кросс-собранный
для MinGW. Соблазн взять родные CNG и Schannel отброшен сознательно — это вторая
реализация форматов, то есть ровно та беда, ради которой ядро писалось один раз.

Критерий: файл с кириллицей в имени уезжает с рабочей станции на серый сервер и
обратно, Ctrl-C и повторный запуск продолжают с того же места.

### M1.6 · Соседство с MeetUp на одном сервере — сделано

Ferry умеет вставать **за чужой nginx**: `--behind-proxy <сеть>` не поднимает
свой прокси, подключает приложение к сети соседа под алиасом `ferry-app` и
не трогает порты. Соседу кладётся готовый server-блок
(`Server/proxy/ferry.conf.example`), а его certbot добавляет имя Ferry в тот
же сертификат (`--extra-domain` на стороне MeetUp).

Получается `https://fferry.ru/` — без порта, с настоящим сертификатом, один
TLS-терминатор и одно продление на оба сервиса.

Что всплыло по дороге, и чего не было видно из плана:

- **Оба проекта давали compose одно имя — `server`**, потому что оно берётся
  от каталога, а compose-файлы у обоих лежат в `Server/`. На сервере с MeetUp
  `docker compose up` в Ferry счёл бы его контейнеры своими и заменил их:
  совпадали и имя проекта, и имена сервисов (`app`, `proxy`). Проверка портов
  этого бы не поймала — она увидела бы порты как «свои». Лечится явным
  `name: ferry`. Имя MeetUp не трогали: оно уже привязано к томам с
  сертификатами, и переименование осиротило бы их.
- **Сервер по умолчанию доставался соседу.** `include` чужих конфигов стоял
  до блоков MeetUp, а первый описанный блок для `listen 443` становится
  default — и MeetUp молча отдавал весь неопознанный трафик Ferry. Помечено
  явным `default_server`; теперь от порядка ничего не зависит.
- **Сервис соседа тоже называется `app`.** В общей сети compose вешает алиас
  по имени сервиса, и `app` указывал бы сразу на два контейнера. Поэтому у
  Ferry в общей сети свой алиас `ferry-app`.
- **`$host` в nginx отдаёт имя без порта.** Приложение строит по нему адрес
  релея для установщиков, и на нестандартном порту клиенту прописывался адрес
  без порта — то есть в никуда. Везде `$http_host`.
- **Старое «есть каталог — сертификат не трогаем»** в certbot у MeetUp
  означало, что добавленный `--extra-domain` не попадал в сертификат никогда.
  Сосед получал ошибку имени, а причина была не видна: сертификат-то есть и
  валиден. Теперь запрос идёт всегда, но с `--keep-until-expiring`, а путь
  `live/` закреплён через `--cert-name`.

Проверено целиком: [`tests/shared-proxy.sh`](../tests/shared-proxy.sh) —
10 проверок, от «прокси соседа встаёт с пустым каталогом» до «вебсокет
проходит через общий nginx».

### Замечания с первого боевого развёртывания

Три вещи всплыли только на живом сервере, и все три исправлены.

- **Кросс-сборка OpenSSL тянула 192 МБ вместо 53.** `git clone --depth 1`
  разворачивает рабочее дерево целиком; на медленном канале шаг занял
  841 секунду. Заменено на тарболл с запасным зеркалом, плюс `no-apps`:
  стадия стала 65 секунд. Появился и `--skip-windows` — тогда BuildKit
  тяжёлую стадию вовсе не запускает.
- **Сосед перестал отвечать сразу после запуска Ferry.** Это тот самый
  конфликт имён проектов; `name: ferry` его закрывает, а `update.sh` теперь
  ещё и находит контейнеры, поднятые под старым именем, и объясняет порядок
  восстановления вместо того, чтобы молча продолжить.
- **Приглашение обещало «д», а работало только «y».** Причин оказалось две:
  кодовая страница ВВОДА консоли Windows задаётся отдельно от вывода (одного
  `SetConsoleOutputCP` мало), а проверка «есть ли терминал» смотрела на
  вывод вместо ввода — и вопрос не задавался, стоило перенаправить вывод в
  файл. Теперь принимаются UTF-8, CP1251 и CP866, а условие стоит на вводе.

### Замечания со второго развёртывания: приём полз, клиент не верил сертификату

Две вещи, обе в клиенте и обе под Windows.

**Приём шёл 0,33 МиБ/с при отдаче в 30 МБ/с.** Виноваты два места, которые
поодиночке выглядят безобидно, а вместе дают двухсоткратную потерю.

- `WebSocketClient::pump()` выходил из цикла чтения, как только чтение
  вернуло меньше, чем размер буфера. На голом TCP это почти правда, на TLS
  не правда никогда: `SSL_read` отдаёт не больше **одной записи**, то есть
  16 КиБ при буфере в 64, — условие выхода срабатывало всегда, с первого
  оборота. Получался один заход в цикл событий на каждые 16 КиБ.
- `LivePanel::update()` перерисовывал панель на каждом обороте цикла без
  всякого ограничения по частоте. Запись в консоль Windows — синхронный
  вызов к conhost; на 16 КиБ полезных данных приходилась полная
  перерисовка с картой тома.

Почему это не поймали раньше: **отдача от того же дефекта не страдает**.
Отправитель за один оборот цикла успевает отдать всё, что влезает в сокет
(мегабайты), и панель у него стоит копейки на мегабайт. А сценарные тесты
гоняют клиента с перенаправленным выводом, где панель молчит по
определению, — и там даже со старым `pump()` получается 190 МиБ/с.
Замер на том же томе в 200 МиБ, локальный релей, настоящая консоль:

| | вывод в файл | настоящая консоль |
|---|---|---|
| было | 190 МиБ/с | **0,33 МиБ/с** |
| стало | 190 МиБ/с | **110 МиБ/с** |

Исправлено: `pump()` вычерпывает сокет до конца (выход только по «данных
больше нет») с потолком в 8 МиБ на оборот; панель рисуется не чаще десяти
раз в секунду, а придержанный последний кадр дорисовывает `finish()`.
Заодно `pump()` спрашивает `SSL_pending()`: расшифрованный хвост внутри
OpenSSL ядру не виден, и `select` про него молчит — без этой проверки цикл
мог уснуть на полном таймауте с готовыми данными в руках.

**Клиент под Windows отвергал любой сертификат**, включая безупречный
Let's Encrypt: «unable to get local issuer certificate» на домене, который
браузер открывает без единого замечания. Причина не в сертификате, а в том,
что `SSL_CTX_set_default_verify_paths()` ведёт по пути, вкомпилированному
при сборке OpenSSL, — а собирается он у нас внутри докер-образа, и на
машине пользователя этого каталога нет. Хранилища корней у клиента,
таким образом, не было вообще. Теперь корни берутся из системных хранилищ
Windows (`ROOT` и `CA`, через `platform::systemRootCertificates()`), а на
Linux по-прежнему работает штатный путь OpenSSL. Отдельно стоит запомнить
форму, в которой это проявляется: **`--insecure` «помогает»** — и потому
выглядит как проблема сервера, хотя проблема целиком на стороне клиента.

### Папки и деинсталляция — вне плана, сделано

Две вещи вклинились по прямому запросу, до M3.

**Папки (M5 в части CLI).** Оказалось дешевле, чем стояло в плане:
манифест-дерево (`kind: "tree"`, опись, `sanitizeRelPath`) был написан и
покрыт тестами ещё в M1 — именно затем, чтобы потом не менять формат.
Добавилось три вещи:

- `core/VolumeLayout` — раскладка тома по файлам. В ядре, а не у клиента,
  и это важно: разойдись две реализации на один байт — и хеши сойдутся
  (чанки-то те же), а файлы на диске окажутся склеены со сдвигом;
- `Cli/VolumeFile` — том как одно байтовое пространство поверх одного файла
  или дерева. После этого ни отправитель, ни получатель больше не знают,
  сколько там файлов, — ровно как и сервер;
- `Cli/Tree` — обход каталога в опись, с лексикографической сортировкой
  по полному пути (§3: при ней любой подкаталог — непрерывный диапазон
  байт, что понадобится для выборочной загрузки).

Недокачка дерева — это **каталог** `<имя>.ferry-part`, который в конце
переименовывается целиком: полутом под настоящим именем хуже
отсутствия тома. Файлы создаются лениво, при первой записи: сорок
тысяч файлов, созданных заранее, — это сорок тысяч системных вызовов
до первого принятого байта, и человек в это время смотрит на замерший
ноль процентов.

**`ferry uninstall`.** Чистая деинсталляция возможна ровно потому, что
Ferry ничего не оставляет на диске сверх того, что положил
установщик: список следов конечен и показывается целиком до вопроса.

Две вещи оказались неочевидными:

- **Windows не даёт удалить образ запущенного процесса**, зато даёт его
  переименовать. Сначала убираем файл с его имени (с этого мгновения
  `ferry` в PATH уже нет), потом оставляем поручение добить остаток. На
  POSIX этого не нужно вовсе: имя из каталога исчезает сразу, а инод живёт
  до конца процесса;
- **PATH убираем только на Windows**, и это не асимметрия ради
  асимметрии: `install.ps1` пишет в реестр сам, а `install.sh` в PATH не лезет
  вовсе — он только советует строку для `~/.profile`. Править чужой профиль
  без спросу хуже, чем оставленная строка.

**Что в том не берётся и почему об этом сказано.** Обход с самого начала
собирал список пропущенного, но никто его не печатал: комментарий в `Tree.h`
обещал то, чего код не делал. Теперь список выводится **до ссылки** — пока
ещё можно передумать; узнать об этом от получателя сильно хуже.

Заодно закрылась дыра рядом: всё, что не каталог и не обычный файл, раньше
попадало в опись как файл нулевого размера — и FIFO, и сокет, и запись,
о которой система не стала рассказывать. Правдоподобная пустота хуже
честного пропуска: `DirEntry::isOther` теперь различает эти случаи.

И отдельно — **облачные заглушки Windows**. Файл OneDrive, который ещё не
скачан, — тоже точка переразбора, а значит, по старому правилу «точка
переразбора = ссылка» человек с включёнными «файлами по требованию»
отправил бы почти пустую папку и ничего бы не заметил. Теперь ссылкой
считается только метка `IO_REPARSE_TAG_SYMLINK`/`MOUNT_POINT`, а `RECALL_ON_*`
читается как обычный файл: первое чтение подтянет его из облака, ровно как
при копировании в проводнике. Проверено на настоящих junction’ах, включая
ссылку каталога на самого себя: цикла не возникает, обе записи названы.

### Скорость, переезд релея и хеши на лету — вне плана, сделано

**Откуда было 5 МБ/с.** Не из Ferry. Замеры по порядку:

- На стенде с эмуляцией канала релей выбирает 91 % любой полосы, которую
  ему дали, делит её между получателями честно и не проседает со временем.
  Процессора на это уходит ~0,07 % ядра на МБ/с.
- Старый релей (rus1) отдавал самому себе по localhost 6,5 МБ/с — связка
  nginx + TLS + FerryServer. Тот же стек у нас давал 120 МБ/с на одном
  ядре и опускался до цифр rus1 только при 5 % ядра. Процессор rus1 был
  задушен, и передачи отнимали его у MeetUp.
- Релей переехал в Финляндию (4 ядра, 4 ГБ): напрямую 27,5 МБ/с в один
  поток и 39 в восемь.
- Потолок в ~10 МБ/с теперь ставит туннель Xray на машине отправителя: весь
  трафик, включая отечественный релей, уходил через него. Лечится
  маршрутом `direct` для домена релея в клиенте Xray.

**Хеши на лету.** Отправитель больше не читает том целиком до ссылки:

- ссылка появляется сразу — 0,3 с на томе в 5 ГБ при скорости диска как у
  HDD, где раньше ждали бы ~51 с;
- хеши считает `Cli/Hasher`: один поток читает том подряд, до четырёх
  считают BLAKE3, диск и процессор работают одновременно;
- список уходит сегментами под `K_meta` со своей меткой у каждого сегмента
  (§1 protocol.md), чанк никогда не уходит раньше своего хеша, и релей это
  проверяет;
- когда всё посчитано, отправитель шлёт итоговые манифест и список в
  прежнем виде, и раздача становится обычной — в том числе для клиентов,
  которые про хеши на лету не знают;
- до этого момента такие клиенты получают `preparing`, «зайдите через
  минуту», а не сломанный том.

Неочевидного было четыре вещи:

- **Nonce.** Промежуточный манифест (без корня) и итоговый — разные тексты,
  и под одной меткой их шифровать нельзя. Итоговым достались прежние метки,
  промежуточному — новая.
- **Докачка.** Карта принятого привязана к корню, а корня ещё нет. Наивная
  реализация молча стёрла бы недокачку. Теперь такие чанки не считаются
  своими, пока не перечитаны с диска и не сверены с приехавшим хешем.
- **Потоки на Windows.** GCC 12 из MinGW в Debian собран с моделью win32, и
  `std::thread` в нём нет. Вместо смены тулчейна — три примитива в
  `platform/Threads.h` на SRW-блокировках и `CreateThread`.
- **Квота релея.** Со старым релеем откат к подсчёту заранее мог бы делать
  два `POST` на одну раздачу и выбирать общую квоту создания раздач вдвое
  быстрее. Второй заводится только если первый черновик успел истечь.

Проверки: ядро 186, Linux 41 (новый сценарий 16), Windows 11, матрица
старый/новый клиент 4 из 4, новый клиент со старым релеем.

### Отдача на сервер и «не удалось прочитать» — вне плана, сделано

**Отдача.** Релей на fin1 принимает 87 МБ/с через nginx и TLS, так что
сервер ни при чём. Напрямую с ПК на fin1 (RTT 26 мс) голый поток шёл
11,9 МБ/с, а Ferry — 7,5. Пока отправитель читал и шифровал следующий чанк,
в сокет ничего не писалось, а очередь, которую Windows держит сама, на
такой задержке кончалась раньше. Теперь на Windows у сокета явный буфер
отправки 4 МиБ, и отправитель проталкивает данные в сокет после каждого
чанка. Результат — 11,9 МБ/с, ровно как у голого потока. Через туннель VPN
этого не было видно: там TCP кончается на локальном адаптере.
Для замеров мимо туннеля есть `FERRY_TEST_BIND`.

**Архив, который «не удалось прочитать».** Раньше:
- короткое чтение считалось ошибкой, а на сетевых файловых системах оно
  законно — и первый крупный файл, обычно архив, ронял раздачу;
- причина от системы выбрасывалась, и в сообщении оставалось только
  «файл перестал читаться».

Теперь:
- чтение и запись дочитывают до конца;
- временные сбои (файл держит антивирус или другая программа) повторяются
  около трёх секунд;
- каждое сообщение несёт путь и причину с кодом;
- файл, который не открывается, выясняется при описи и уходит в
  «пропущено» с причиной до ссылки, а не роняет раздачу через час;
- на Windows пути длиннее 260 символов получают префикс `\\?\`, а
  `makeDirectories` больше не спотыкается о него и о `\\server\share`.

Проверки: Linux 43 (новый сценарий 17 — нечитаемый файл), Windows 11,
отдельно — занятый zip и путь в 355 символов.

|---|---|
| **Интерактивный установщик для PowerShell** | Сейчас `install.ps1` делает ровно одно: кладёт бинарь и прописывает релей. ## 8. M2 · Веер и две волны

**Критерий приёмки.** Трое качают том на 5 ГиБ. Третий подключается, когда
первые двое прошли 60 %. Он получает том целиком и сходится по BLAKE3;
скорость первых двух не меняется; **счётчик отданных отправителем байт не
превышает объём тома больше чем на 5 %**.

Последнее условие — главное. Без него милестон проходится тривиально
(попросить у отправителя всё заново), и ровно этим Ferry перестал бы
отличаться от обычного релея.

### Что мешает сегодня

Получатель, чей курсор оказался левее начала окна, получает честный отказ
`no_source` — [`TransferSession::pump()`](../Server/core/TransferSession.cpp).
Окно по умолчанию 256 МиБ: на томе в 5 ГиБ опоздать можно на пять процентов.
Двое друзей, начавших не одновременно, — уже не работает.

### Разбить на два захода

**M2.1 · Опоздавший доезжает.** Источники — окно и отправитель. Появляются
`have`, `request`, `flow`, раздельные кредиты на живой поток и на догон,
эвристика «догон против двух волн». Отказ `no_source` исчезает.

**M2.2 · Опоздавший обходится отправителю бесплатно.** Добавляется
`serve` — reflected backfill от других получателей, коалесцирование запросов
и потолок на возврат к отправителю. Критерий приёмки закрывается целиком.

Делить стоит именно так: M2.1 — это исправление дыры, оно проверяется
«приехало / не приехало» и не требует второго источника вообще. M2.2 — это
защита тезиса, и проверяется она счётчиком отправителя. Смешав их, мы бы
отлаживали планировщик и новый источник одновременно.

### Ядро: множество чанков

Новый общий тип `core/ChunkSet.{h,cpp}` — битовая карта на `chunkCount` бит
плюс перевод в диапазоны и обратно.

Нужен обеим сторонам и именно поэтому живёт в ядре: сервер держит им карту
каждого получателя, клиент — свою карту принятого (сейчас это самодельный
`ChunkMap` внутри [`Receiver.cpp`](../Cli/Receiver.cpp), и он уже умеет
почти всё нужное — его туда и переносим). Одна реализация, потому что
диапазоны ездят по проводу: разойдись они в трактовке границ, и ошибка
проявилась бы дыркой в томе, а не исключением.

Границы диапазонов — **включительные с обеих сторон**, `[a, b]`, как в §8
проектного документа. Размер: у тома в 1 ТиБ при чанке 4 МиБ это 262 144
бита, то есть 32 КиБ на получателя. При потолке в восемь получателей —
четверть мегабайта на раздачу, на фоне окна в 256 МиБ незаметно.

### Протокол: шесть сообщений и два поля в `hello`

Получатель → сервер:

```jsonc
{ "type": "have",    "ranges": [[0,40],[512,817]] }   // что у меня есть
{ "type": "request", "ranges": [[41,511]], "budget_bytes": 8388608 }
{ "type": "flow",    "live_budget": 8388608, "backfill_budget": 4194304 }
{ "type": "bad_chunk", "index": 57 }                  // прислали мусор
```

`flow` уехал из первого захода в M2.2, и это сознательно. Он делит
канал получателя между двумя волнами — а второй волны пока нет, и
делить нечего. Сообщение, единственный отправитель которого — его
собственный тест, хуже честного отсутствия: он выглядит рабочим, не
будучи проверенным ни разу на настоящей задаче.

Сервер → получателю:

```jsonc
{ "type": "serve", "ranges": [[0,40]], "budget_bytes": 4194304 }
{ "type": "stats", "rate_bps": 118000000, "eta_ms": 42000,
  "src": { "window": 0.71, "peers": 0.29, "sender": 0.0 } }
```

И два поля в `hello`:

```jsonc
{ "type": "hello", "id": "…", "proof": "…", "have": [[0,40]],
  "features": ["backfill"] }
```

Три вещи, которых нет в §8 проектного документа и которые стоит объяснить.

**`features` в `hello`.** Сервер шлёт `serve` только тем, кто объявил
`backfill`. Без этого поля клиент M1, получив `serve`, молча его
проигнорирует — а сервер будет ждать чанков, которые не придут, и опоздавший
встанет насмерть по вине совершенно постороннего участника. Старые клиенты
при этом продолжают качать как качали: они просто не становятся источниками.

**`bad_chunk`.** В §8 его нет, потому что в §8 источник один и он доверенный.
Как только чанк может приехать от другого получателя, появляется тот, кто
пришлёт мусор — по злому умыслу или из-за битой памяти. Сервер проверить
ничего не может: он не знает ключа и не должен знать. Проверяет получатель,
по списку хешей, — **и это уже работает**. Менять надо реакцию: сейчас
несошедшийся хеш валит всю передачу (`chunk_mismatch`), а в M2 он обязан
означать «этот чанк выбросить, у этого источника больше не спрашивать,
попросить заново». Валить передачу из-за чужого вранья — это отдать любому
участнику право её убить.

**`have` вместо `have_upto`.** Поле `have_upto` из M1 остаётся понятным
серверу, чтобы не ломать старых клиентов, но новый клиент шлёт полные
диапазоны: после первого же backfill принятое перестаёт быть префиксом.

### Сервер: планировщик

`TransferSession` получает второй контур. Живой поток остаётся как есть —
он и сейчас правильный.

```
живая волна    RingWindow ──► всем подписчикам, по мере прихода
               от отправителя — как сейчас

вторая волна   источник для недостающего диапазона, по приоритету:
               1. окно, если начало ещё не вытеснено   бесплатно
               2. другой получатель          (serve)   аплоад пира
               3. отправитель                (need)    ≤30 % его кредита
```

Что добавляется:

- **`ChunkSet` на каждого получателя** — что у него есть. Обновляется по
  `have` и по фактической отправке.
- **Таблица ожиданий**: `индекс чанка → кто его ждёт`. Это и есть
  коалесцирование: два опоздавших, которым нужен чанк 5, дают **один**
  запрос к источнику и две отправки. Без таблицы reflected backfill
  вырождается в N запросов на чанк, и лечить это потом пришлось бы
  переписыванием планировщика.
- **Буфер backfill** — отдельный от окна и маленький (по умолчанию 32 МиБ).
  Отдельный принципиально: чанк, приехавший по `serve`, не имеет права
  двигать живое окно, иначе догон опоздавшего выталкивал бы из окна тех, кто
  идёт вовремя, и они тоже становились бы опоздавшими. Такую лавину лучше
  не изобретать.
- **Потолок на возврат к отправителю.** Кредит `need` разделяется на две
  полосы: живую и догонную, и догонная не больше 30 % от живой. Группа
  проседает на треть, а не встаёт.
- **Выбор источника** для каждого недостающего диапазона по таблице выше,
  с проверкой, что у кандидата есть свободный аплоад (`pendingBytes()`
  ниже порога) и что он не в чёрном списке по `bad_chunk`.

Две ловушки, которые видно уже сейчас.

`slowestCursor()` — понятие **префиксное**, и с backfill'ом оно перестаёт
описывать получателей: у них появляются дырки. Курсор должен остаться
курсором **живой волны** и только ею, а вытеснение окна — считаться по нему
же. Иначе получатель, тянущий начало тома второй волной, притормозит окно
для всех — ровно то, чего drop-behind призван не допускать.

`m_receivers` сейчас `QList` и обходится линейно на каждый `pump()`. С
таблицей ожиданий обходов станет больше; при восьми получателях это по-
прежнему ничто, но структуру стоит выбрать сразу так, чтобы не переделывать.

### Отправитель: научить отдавать назад

Нашлось при разборе вопроса «что будет, если второй получатель придёт,
когда первый уже всё забрал». Отправитель M1 **физически не умеет**
повторно отдать чанк, который уже отдал, и это не оплошность, а прямое
следствие того, что в M1 других сценариев не было:

```cpp
int64_t needUpTo = -1;                 // верхняя граница просьбы
uint64_t nextToSend = 0;               // монотонный курсор
while (int64_t(nextToSend) <= needUpTo && …) { … ++nextToSend; }
```

`need` сворачивается в одно число — самую правую границу, — а курсор
только растёт. Попроси сервер чанк 5, когда `nextToSend` уже 5000, —
отправитель молча ничего не сделает, и опоздавший будет ждать вечно.

Значит в M2.1, помимо серверной части, нужна переделка на стороне
отправителя: вместо пары «граница + курсор» — **две очереди
диапазонов**, живая и догонная. `need` приобретает необязательное поле
`lane`; отсутствие поля — это `live`, и тогда релей M1 остаётся понятным.
Живая волна выбирается до конца и только потом догон: иначе один
опоздавший тянул бы начало тома впереди всех, кто качает вовремя.

Заодно это снимает ограничение, о котором в M1 никто не думал: `need` на
уже отданный диапазон терялся бесследно, то есть сторожевой таймер
сервера умел перепросить только то, что ещё впереди.

И ещё одно следствие, важное для критерия приёмки: у отправителя
появляются **два счётчика** вместо одного — сколько тома отдано хоть раз
и сколько байт ушло в сеть вообще. Разница между ними и есть то число,
которое проверяет сценарий 10; в панели она показывается строкой
«повторно N» и только тогда, когда повторы есть.

### Клиент: получатель становится источником

Главное здесь уже готово и досталось даром — **запись вне порядка**.
`fileWriteAt` по смещению чанка и битовая карта рядом с недокачкой
появились в M1 ради докачки после обрыва, и они же есть то, ради чего в
браузере городят OPFS и File System Access.

Что добавляется:

- **Ответ на `serve`.** Получатель читает чанк из собственной недокачки,
  **зашифровывает его заново** и отдаёт серверу. Ключ, nonce
  (`prefix ‖ index`) и AAD у него те же, что у отправителя, а AES-256-GCM
  детерминирован — значит шифротекст получится **байт в байт тот же самый**.
  Хранить шифротекст не нужно, повторное использование nonce здесь не
  ослабление (тот же ключ, тот же nonce, тот же открытый текст — та же
  запись). Именно это делает сидирование бесплатным по месту.
- **Общий `ChunkPump`** вместо копии кода: чтение по смещению, шифрование,
  отправка фрейма — одно и то же у отправителя и у сида.
- **Две волны в панели.** `Seg::FromPeer` в [`Term.h`](../Cli/ui/Term.h)
  заведён под это ещё в M1 и до сих пор не использован; карта тома
  наконец начнёт показывать, что откуда приехало. Плюс строка `stats`:
  сколько процентов пришло из окна, от пиров и от отправителя.
- **`ferry get --seed`** — не выходить после приёма, остаться источником до
  `Ctrl-C`. Пять строк поверх уже написанного, а без этого сценарий
  приёмки не поставить: том должен быть у кого-то, кроме отправителя.
- **Несошедшийся хеш больше не фатален** (см. `bad_chunk` выше).

### Эвристика: догонять или две волны

Из §6 проектного документа:

```
если  missing_prefix < 0.2 × remaining_tail   →  последовательный догон
иначе                                         →  две волны
```

Решает **сервер**, при подключении и заново на каждом сторожевом такте: он
один знает и положение живого потока, и карту каждого получателя, и кто
свободен отдавать. Получателю роль сообщается в `hello_ok`
(`"role": "leech" | "catching" | "seed"`) — ему это нужно только чтобы
нарисовать панель; писать байты он в любом случае будет туда, куда велит
индекс.

### Проверки

В [`tests/scenarios.sh`](../tests/scenarios.sh) добавляется пять сценариев.
Первый закрывает M2.1, остальные — M2.2.

| № | Сценарий | Что доказывает |
|---|---|---|
| 9 | Опоздавший при окне 8 МиБ и томе 200 МиБ — **сделан** | `no_source` исчез; опоздавший доезжает |
| 10 | Двое опоздавших при живом `--seed`-источнике — **сделан** | **Тезис продукта** плюс коалесцирование |
| 11 | Скорость первых двух до и после подключения третьего | Опоздавший не тормозит группу |
| 12 | Единственный пир с началом тома отваливается посреди backfill — **сделан** | Падение назад к отправителю; том всё равно приезжает |
| 13 | Пир отдаёт испорченный чанк | Получатель отвергает чанк, а не передачу; источник меняется; том сходится |

Сценарий 13 проще всего поставить отдельной сборкой клиента с флагом
«портить каждый сотый чанк» — врать по-настоящему должен клиент, иначе
проверка выродится в проверку самой проверки.

В сценарии 10 опоздавших именно двое, и это не для красоты: счётчик
отданного у сида должен вырасти на **один** том, а не на два. Один
опоздавший прошёл бы и без коалесцирования.

## 10. Подводные камни, которые видно уже сейчас

1. **glibc.** Разобрано в §4: клиент собирается на bullseye, иначе не пойдёт на
   Ubuntu 22.04.
2. **Самоподписанный сертификат ломает `curl | sh`.** Если у белого сервера нет
   домена, установка клиента потребует `curl -k`, а сам клиент — флага
   `--insecure`. Поддержим явно и с предупреждением, но **домен на релее сильно
   упрощает жизнь** — и он же понадобится в M3 для браузера.
3. **Отправитель должен жить, пока идёт раздача.** У CLI это `tmux`/`systemd`, а
   не «не закрывайте вкладку». В `send` полезно сразу печатать подсказку про
   `tmux new -s ferry`.
4. **Память сервера.** Окно по умолчанию 256 МиБ на раздачу (§6) — на VPS с 1–2 ГБ
   это две-три раздачи. Глобальный потолок и динамическое ужимание окна нужны уже
   в M1, иначе первый же тест на 5 ГБ уронит сервер в своп.
5. **Свой WS-клиент.** Самая вероятная точка «два часа на ерунду»: маскирование,
   64-битная длина для 4 МиБ фреймов, ping/pong, неблокирующий OpenSSL
   (`SSL_ERROR_WANT_READ` на записи — да, так бывает). Пишем аккуратно один раз.
6. **`#` в ссылке.** Шелл съест всё после решётки, если не заквотить. `ferry send`
   печатает ссылку **уже в кавычках**, а `ferry get` принимает и разобранный вид
   (`--id`/`--key`) на случай, если кто-то всё равно потеряет фрагмент.

## 11. Решено на старте

| Вопрос | Решение |
|---|---|
| Порядок клиентов | **CLI первым**, веб-получатель в M3 |
| Сборка CLI | **Без Qt, один бинарь** |
| TLS на релее | **Домен будет позже.** Пишем оба режима сразу, тестируем на самоподписанном, переключаемся флагом `--domain`, когда домен появится |
| Объём захода | **M1** (один→один), дальше решаем по факту |

Из третьего пункта следует конкретное требование к M1: клиент обязан уметь
`--insecure` (и `FERRY_INSECURE=1`) — **явно, шумно и с предупреждением в выводе**,
а `install.sh` должен уметь ставиться через `curl -k`. Когда появится домен, оба
флага перестают быть нужны и ничего переписывать не придётся.
