# Ferry

**Паром для файлов.** Релей больших файлов и папок через собственный сервер: ничего
не хранится на диске, всё шифруется на устройстве, один отправитель кормит
сколько угодно получателей — и каждый качает на полной скорости, когда бы он ни
подключился.

Проектный документ: что делаем, чего не делаем, как устроено, в каком порядке
строим. Написан так, чтобы по нему можно было сразу начинать макет.

## 1. Задача и позиционирование

### Боль

Скорость до мессенджеров и облаков режут. Файл на 5 ГБ отправить некуда: почта
не примет, облако отдаст по 200 КБ/с, торрент — это про публичные раздачи и
требует клиента, P2P-сервисы упираются в NAT и в аплоад отправителя.

### Формула

> **Локальная замена торрента для одной раздачи между своими: ссылка, браузер,
> ничего не установлено, сервер свой.**

Ferry — не файлообменник (файлообменник хранит) и не торрент (у торрента рой,
трекеры и история). Это **паром**: пришёл, перевёз, ушёл, на берегу ничего не
осталось.

### Три обещания продукта

1. **Сервер не хранит ничего.** Ни файла, ни имени файла, ни метаданных на диске.
   В оперативке — идентификатор раздачи, сокеты и скользящее окно байтов, которое
   тут же вытесняется. Перезапуск сервера = все раздачи умерли, и это нормально.
2. **Отправитель отдаёт байт один раз.** Сколько бы человек ни качало и когда бы
   они ни подключились.
3. **Никакой регистрации.** Ни почты, ни телефона, ни логина. Владение раздачей —
   это владение случайным токеном в памяти вкладки.

### Кому

Свои люди: переслать проект, отснятый материал, дамп, сборку, папку с фотками.
Два-пять получателей, не две тысячи.

## 2. Границы: чего мы НЕ делаем

Это самый важный раздел документа. Всё, что ниже, — сознательно отрезано, чтобы
проект не превратился в самодельный BitTorrent.

| Не делаем | Почему |
|---|---|
| **DHT, трекеры, обнаружение пиров** | Единственный координатор — сервер. Пиры друг о друге не знают и не могут узнать. |
| **Постоянный рой, история раздач, реанонс** | Раздача живёт ровно столько, сколько описано в §5, и не воскресает. |
| **rarest-first, tit-for-tat, choking, оптимистичная раскачка** | Планировщик у нас тривиальный и последовательный: §6. Нет экономики обмена — нет и всей её сложности. |
| **Прямые соединения между пирами (WebRTC/STUN/TURN)** | Весь трафик идёт через сервер. Нет NAT-траверсала, нет ICE, нет TURN-счетов. Пир, который «раздаёт», просто загружает чанки обратно на сервер. |
| **Хранение на сервере дольше окна** | Окно — это буфер джиттера на секунды, а не кэш. |
| **Аккаунты, регистрация, профили, квоты пользователя** | Анонимность по умолчанию — часть продукта. |
| **Возобновление раздачи после смерти сессии** | Сессия умерла — ссылка мертва навсегда. Новая раздача = новая ссылка и новый ключ. |
| **Сжатие на лету** | Файлы в основном уже сжаты; CPU дороже, чем выигрыш. Папки пакуются без компрессии (store). |
| **Предпросмотр содержимого *на сервере*** | Сервер физически не может — у него только шифротекст. Клиент, наоборот, показывает полное дерево файлов до начала загрузки и даёт выбрать, что качать (§3). |

## 3. Модель данных: том, чанки, манифест

### Том (volume)

Всё, что раздаётся, — один **том**: непрерывное логическое байтовое пространство.

- Один файл → том = этот файл.
- Папка → том = конкатенация файлов в порядке манифеста, без выравнивания и без
  заголовков между ними.

Это ключевое решение: **сервер всегда видит один линейный поток из N чанков и
понятия не имеет, один там файл или тысяча.** Вся логика окна, курсоров и
backfill остаётся ровно той же для файла и для папки.

```
Манифест (зашифрован, сервер не читает):
  [0]  src/main.cpp      1 240 B      offset 0
  [1]  src/main.h           820 B     offset 1 240
  [2]  assets/logo.png  184 320 B     offset 2 060
  ...
Том:  [ файл0 ][ файл1 ][ файл2 ] ... = 8 421 376 байт
Чанки: 1 МиБ → 9 чанков (последний неполный)
```

### Чанки

| Размер тома | Чанк |
|---|---|
| < 64 МиБ | 256 КиБ |
| 64 МиБ – 4 ГиБ | 1 МиБ |
| > 4 ГиБ | 4 МиБ |

Размер фиксируется в `offer` и не меняется. Оверхед AEAD — 16 байт на чанк
(0,0015 % при 1 МиБ).

### Манифест

```jsonc
{
  "v": 1,
  "kind": "file" | "tree",
  "name": "project",              // имя файла или корневой папки
  "total": 8421376,               // байт в томе
  "entries": [                    // только для kind:"tree"
    { "p": "src/main.cpp", "s": 1240, "m": 1726000000 },
    { "p": "src/main.h",   "s": 820,  "m": 1726000000 },
    { "p": "empty/",       "s": 0,   "d": true }      // пустая директория
  ]
}
```

Правила:

- `p` — **относительный POSIX-путь**, всегда с `/`, без ведущего слэша, без
  `.`/`..`, без буквы диска, без символов `< > : " | ? *` и управляющих.
- Порядок `entries` задаёт раскладку тома. Сортировка — **лексикографическая по
  `p`**, и это не вкусовщина: при таком порядке любой подкаталог оказывается
  непрерывным диапазоном байт, а значит «скачать только папку `2024/отчёты/`» —
  это один сплошной запрос диапазона, а не решето (§3, «Выборочная загрузка»).
- Симлинки не поддерживаются. Реализовано вторым вариантом: пропускаются
  с перечислением в UI до того, как появится ссылка. Разыменование отвергнуто:
  оно либо утащит полдиска, либо уйдёт в цикл по самоссылке.
  Туда же и всё, что не обычный файл (FIFO, сокеты, устройства): размера у
  них нет, а чтение из FIFO встало бы насмерть и увезло за собой всю раздачу.
  Исключение — облачные заглушки Windows (OneDrive, `RECALL_ON_*`): формально
  это точки переразбора, но по смыслу — обычные файлы, и пропускать их значило
  бы отправить пустую папку человеку, у которого всё вроде бы на месте.
- Права доступа не переносим (в браузере их всё равно нет).

**Санитизация на приёме обязательна** (класс уязвимостей Zip Slip): получатель
заново валидирует каждый `p` перед записью и отклоняет том целиком при первом
нарушении, а не «чинит» путь молча. Отдельно — резервные имена Windows (`CON`,
`PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9`), завершающие точки и пробелы.

### Ограничения v1

- До 100 000 записей в манифесте (дальше UI и память браузера начинают страдать).
- Манифест до 8 МиБ в сжатом виде.
- Том до 1 ТиБ (см. §7 про место на диске получателя — это станет узким местом
  раньше).

## 4. Криптография и целостность

### Ключи

```
K  = 32 случайных байта (CSPRNG)      ← живёт во фрагменте ссылки, на сервер не уходит

K_data     = HKDF-SHA256(K, info="ferry/v1/data")      шифрование чанков
K_meta     = HKDF-SHA256(K, info="ferry/v1/meta")      шифрование манифеста и списка хешей
V          = HKDF-SHA256(K, info="ferry/v1/verifier")  32 байта → ОТДАЮТСЯ серверу
```

`V` — односторонняя производная от `K`. Сервер получает `V`, чтобы проверять, что
подключившийся действительно знает ключ (см. §5), но из `V` нельзя получить `K` и
нельзя расшифровать ни байта.

### Шифрование чанка

**AES-256-GCM** (WebCrypto, аппаратное ускорение везде; тот же примитив, что в
MeetUp — одна крипто-культура на два проекта).

```
nonce (12 байт) = [ transfer_nonce_prefix : 4 ][ chunk_index : 8, big-endian ]
AAD             = [ version:1 ][ chunk_index:8 ][ total_chunks:8 ]
```

- `transfer_nonce_prefix` — 4 случайных байта на раздачу. Повтор nonce невозможен:
  индекс уникален внутри тома, префикс уникален между томами.
- `total_chunks` в AAD закрывает атаку обрезания (нельзя выдать укороченный том за
  целый), `chunk_index` — атаку перестановки.

Это конструкция STREAM (как в `age` и Tink), проверенная и без сюрпризов.

### Целостность: плоский список хешей

Не Merkle-дерево и не Bao — для наших размеров хватает **плоского списка**:

```
hashes = [ BLAKE3(plain_chunk_0), BLAKE3(plain_chunk_1), ... ]   // 32 байта на чанк
root   = BLAKE3(hashes)                                          // 32 байта, в ссылку не кладём
```

- `root` лежит в **зашифрованном** манифесте — то есть сервер не видит даже
  content-id (иначе он стал бы идентификатором «того же файла» между раздачами).
- Список хешей передаётся первым, зашифрованный `K_meta`. Получатель сверяет
  `BLAKE3(hashes) == root`, дальше каждый чанк проверяется за O(1) против
  `hashes[i]` — **сразу, независимо и в любом порядке**.

Именно это делает безопасным приём чанков от других получателей (§6): подсунуть
мусор невозможно, подмена ловится на месте.

Размер накладных: 32 байта на чанк → 640 КБ для 20 ГБ при чанке 1 МиБ. Приемлемо.
Если когда-нибудь понадобятся терабайтные тома — переезжаем на Bao/BLAKE3 tree с
инкрементальными доказательствами, интерфейс не меняется.

### Ссылка

```
https://ferry.example/t/<id>#<key>
                        │       └── 32 байта base64url — НИКОГДА не уходит на сервер
                        └────────── 16 байт base64url — публичный id раздачи
```

Фрагмент (`#…`) не попадает ни в HTTP-запрос, ни в логи, ни в `Referer`, ни в
историю прокси. Полная длина ~80 символов — нормально для QR.

### Режим «ссылка отдельно, пароль отдельно»

Если отправитель задал пароль, ссылка отдаётся **без фрагмента**, а ключ выводится
из пароля:

```
K = Argon2id(password, salt, m=64MiB, t=3, p=1)
```

`salt` (16 байт) сервер держит в оперативке и отдаёт публично — это соль, она не
секрет. Позволяет прислать ссылку в мессенджере, а пароль продиктовать голосом.

**Честная оговорка, которую нужно написать прямо в интерфейсе:** этот режим
слабее. Ключ теперь стоит ровно столько, сколько стоит пароль, и злой сервер
(или тот, кто его захватил) может перебирать офлайн. Требовать парольную фразу от
пяти слов, короткие пароли не принимать.

## 5. Контроль доступа и жизненный цикл раздачи

Самый тонкий раздел. Разбираем твой вопрос: «кто считает оставшиеся
использования, если отправитель ушёл, а сиды остались».

### Ответ: считает сервер, и неоднозначности не возникает

Всё соединяется **через сервер** — прямых связей между пирами нет (§2). Значит
сервер по построению видит каждое подключение и является единственным
авторитетом. Счётчик использований — это поле в объекте сессии в оперативке,
с ровно той же продолжительностью жизни, что и сама раздача. Сид не даёт доступ,
сид только отдаёт байты по команде сервера.

Это не «состояние на сервере» в том смысле, которого ты избегаешь: на диск ничего
не пишется, при перезапуске всё исчезает. Ты сам это и предложил — «сервер в
оперативке хранит идентификатор раздачи и привязанные вебсокеты и ещё что-то
служебное». Счётчик и есть это «служебное».

### Что лежит в сессии (RAM, ~200 байт + окно)

```cpp
struct TransferSession {
    QByteArray id;              // 16 байт, публичный
    QByteArray verifier;        // V, 32 байта — проверка владения ключом
    QByteArray ownerToken;      // 32 байта, знает только отправитель
    QByteArray passwordSalt;    // 16 байт, если включён парольный режим

    quint64 totalBytes, chunkSize, totalChunks;
    QByteArray encryptedManifest;   // шифротекст, сервер не читает
    QByteArray encryptedHashList;   // шифротекст, сервер не читает

    // политика
    int      usesLeft;          // -1 = без лимита
    qint64   expiresAtMs;
    bool     requireApproval;
    bool     leaveOpen;         // делегирование
    int      maxConcurrent;

    ClientSession*        sender;     // nullptr, если отправитель ушёл
    QList<ClientSession*> receivers;
    RingWindow            window;     // единственное, что весит
};
```

### Проверка владения ключом — без раскрытия ключа

Проблема: сервер не знает `K`, значит не может отличить настоящего получателя от
бота, который дёрнул URL без фрагмента. А раз не может — любой, кто увидел
ссылку без фрагмента (превью-бот мессенджера, прокси), сожжёт использование.

Решение — challenge-response на `V`:

```
отправитель → сервер (в offer):  V = HKDF(K, "ferry/v1/verifier")

получатель → сервер:  "hello", id
сервер     → получатель:  challenge = 16 случайных байт
получатель → сервер:  HMAC-SHA256(V, challenge)          // V он вывел из K сам
сервер:    сверяет; только теперь списывает использование
```

Сервер не узнаёт `K` (HKDF односторонний), по проводу ничего не повторяется
(challenge разный каждый раз), бот без ключа получает `need_key` и **ничего не
сжигает**.

### Жизненный цикл: отправитель может делегировать

Выбранная модель. Политика задаётся один раз в `offer` и **замораживается** в
момент ухода отправителя.

```
                   ┌──────────────┐
    offer ────────►│   ACTIVE     │  отправитель на связи: он авторитет.
                   │              │  Может: пускать/не пускать, менять
                   └──────┬───────┘  usesLeft и TTL, отозвать раздачу.
                          │
        отправитель отвалился
                          │
          ┌───────────────┴────────────────┐
   leaveOpen=false                  leaveOpen=true
          │                                │
          ▼                                ▼
   ┌─────────────┐                 ┌──────────────┐
   │   CLOSED    │                 │  DELEGATED   │  политика заморожена,
   │ всем sender_│                 │              │  менять её больше НЕКОМУ
   │ gone, конец │                 └──────┬───────┘
   └─────────────┘                        │
                     живёт, пока ОДНОВРЕМЕННО:
                       • есть ≥1 получатель со 100 % тома (сид)
                       • usesLeft ≠ 0
                       • now < expiresAtMs
                     иначе → CLOSED
```

**Возврат владельца.** Отправитель уходит с `ownerToken` в памяти вкладки (и,
по желанию, в `sessionStorage`). Переподключился с этим токеном — снова
авторитет: может добавить использований, продлить TTL, убить раздачу. Это
единственный «аккаунт» в системе: эфемерный, анонимный, не восстанавливаемый.

**Что происходит с `requireApproval` при делегировании.** Подтверждать некому,
поэтому отправитель выбирает это заранее, в `offer`:

- `on_owner_leave: "close"` — при уходе раздача закрывается (по умолчанию, если
  включено подтверждение);
- `on_owner_leave: "freeze"` — подтверждение снимается, дальше пускают всех, кто
  знает ключ, в пределах оставшихся использований.

Никакого «сид подтвердил за отправителя» — этого класса решений в системе нет.

### Что сид НЕ может

Явный список, чтобы не расползалось:

- не может пустить нового получателя;
- не может изменить политику, продлить TTL, добавить использований;
- не может оживить закрытую сессию;
- не может узнать, кто ещё качает (сервер не раскрывает состав);
- не может отдать байты кому-то напрямую — только загрузить их обратно на сервер
  по явному запросу.

Сид — это **канал, а не полномочие**.

### Ещё три ручки

| Ручка | Значение по умолчанию | Зачем |
|---|---|---|
| `uses` | без лимита | Одноразовая ссылка = `uses: 1`. |
| `ttl` | 24 часа | Верхняя граница жизни независимо от всего остального. |
| `max_concurrent` | 8 | Не даёт превратить твой VPS в раздатчик для чужого форума. |

## 6. Ядро: окно, две волны, backfill

### Арифметика, ради которой всё затевается

| Схема | Что получает каждый из N |
|---|---|
| Чистый P2P (FilePizza и подобные) | `аплоад_отправителя / N` |
| **Ferry (релей)** | `min(аплоад_отправителя, свой даунлоад)` — независимо от N |

Плата — исходящий трафик сервера, `N × U`. Но именно он у VPS и есть, а у
домашнего отправителя его нет. Продукт продаёт аплоад сервера, не продавая место
на диске.

### Окно — это буфер джиттера, а не кэш

Сервер держит в RAM кольцевой буфер последних чанков (по умолчанию 256 МиБ на
раздачу, настраивается).

Важно понимать масштаб: при 100 МБ/с окно в 256 МиБ покрывает **2,5 секунды**
разброса между получателями. Этого хватает, чтобы быстрый и медленный клиент не
мешали друг другу, и не хватает ни для какого «позднего подключения». Поэтому:

> **Позднее подключение всегда обслуживается backfill'ом, а не окном.**
> Окно существует, чтобы сглаживать разницу в скорости, и только.

### Drop-behind: медленный не тормозит всех

Окно едет со скоростью **отправителя**, а не самого медленного получателя. Кто
отстал — просто выпал из окна и автоматически перешёл в режим backfill. Один
клиент на мобильном интернете не может придержать группу.

### Две волны — твоя схема, и она правильная

Третий подключился на середине. Он **сразу подписывается на живой поток** (хвост,
который и так летит всем — серверу это не стоит ни одного обращения к источнику)
и **параллельно** тянет пропущенное начало второй волной.

```
том:  [■■■■■■■■■■■■■■■■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□]
                          ▲                          
       ◄── волна 2 ────┐  └── волна 1: живой поток вместе со всеми
        (backfill,     │
         от сидов)     │
```

Почему это лучше «догона по порядку»:

- Хвост получателю достаётся **бесплатно** — эти чанки уже в окне, сервер никуда
  за ними не идёт.
- Загрузка новичка не простаивает ни секунды.
- Отправитель по-прежнему отдаёт байт один раз.

Цена — запись **вне порядка** на стороне получателя. Как это решается — §7.

**Когда две волны не нужны.** Если пропущенный кусок мал относительно
оставшегося, дешевле догнать последовательно и слиться с группой. Правило:

```
если  missing_prefix < 0.2 × remaining_tail   →  последовательный догон
иначе                                         →  две волны
```

### Откуда берутся чанки для backfill (по приоритету)

1. **Из окна** — если начало ещё не вытеснено. Бесплатно.
2. **От других получателей (reflected backfill).** Сервер просит того, у кого
   нужный диапазон уже есть: `serve [a,b]`. Тот загружает чанки обратно на сервер,
   сервер раздаёт их тем, кто ждёт. Стоит простаивающего аплоада получателя и
   трафика сервера. **Отправителю — ноль.**
3. **От отправителя**, повторным чтением с диска — последний рубеж, с жёстким
   потолком (≤30 % его аплоада), чтобы для основной группы скорость просела на
   треть, а не рухнула.

**Коалесцирование обязательно.** Если два новичка ждут чанк 5 — сервер запрашивает
его у источника один раз и раздаёт обоим. Без этого reflected backfill
вырождается в N запросов на один чанк.

Именно пункт 2 делает главное обещание правдой. Без него третий подключившийся
стоит отправителю повторной заливки начала — лучше, чем P2P, но не «бесплатно».
Поэтому reflected backfill — часть v1, а не «улучшение на потом». Он же даёт
делегирование (§5): сид уже умеет отдавать, значит после ухода отправителя
раздача просто продолжает работать тем же механизмом.

### Pull с кредитом

Не отправитель пушит сколько влезет, а сервер просит:

```
сервер → отправителю:  need ranges=[[816,831]] budget=8 МиБ
```

Окно не переполняется, отправитель не заваливает сервер. В браузере чанк читается
лениво — `file.slice(off, off+len).arrayBuffer()`, файл целиком в память не
попадает никогда.

### Backpressure

На каждого получателя — свой курсор; шлём, пока `QWebSocket::bytesToWrite()` ниже
порога (например 4 МиБ). Быстрый качает быстро, медленный медленно, связи нет.

### Защита памяти сервера

```
RAM ≈ Σ(окно каждой раздачи) + мелочь на сессии
```

Жёсткий глобальный потолок; при достижении — новые раздачи получают `server_busy`,
а не своп. Окно динамически ужимается, когда раздач много.

## 7. Сторона получателя: куда пишутся байты

Две волны требуют записи вне порядка, а reflected backfill — ещё и чтения того,
что уже записано. Значит получателю нужен **файл с произвольным доступом**, а не
поток в менеджер загрузок.

### Развилка по возможностям браузера

| Путь | Где | Что даёт |
|---|---|---|
| **A. File System Access API** | Chrome, Edge | `showSaveFilePicker()` / `showDirectoryPicker()` → `createWritable()` с позиционированием. Пишем сразу в конечный файл, произвольный доступ, настоящая докачка, сидирование читает оттуда же. Лучший путь. |
| **B. OPFS (Origin Private File System)** | Firefox, Safari, все | `createSyncAccessHandle()` в воркере — полноценный произвольный доступ в приватном хранилище. По завершении — финальная материализация: поток через Service Worker в штатный менеджер загрузок. Цена: временно 2× места. |
| **C. Последовательный поток** | фоллбэк | Только по порядку, без двух волн и без сидирования. Включается, когда в OPFS не влезает. |

Выбор автоматический: `navigator.storage.estimate()` → если свободного меньше
`1.2 × размер тома`, путь B отключается и включается C с честным предупреждением
в интерфейсе.

**Папки на приёме:**

- путь A: `showDirectoryPicker()` → настоящее дерево на диске;
- пути B/C: собираем на лету **ZIP без сжатия** (store, zip64 для >4 ГиБ) и
  отдаём одним файлом. Центральная директория в конце, поэтому потоковая сборка
  работает штатно.

**Резюм после обрыва.** OPFS/FSA хранит рядом битовую карту принятых чанков.
Переподключились → отправили `have` → продолжили с того же места. Для «интернет
режут, соединения рвутся» это не опция, а базовая функция.

**Важное следствие:** получатель на пути C **не может быть сидом** — байты ушли в
менеджер загрузок и недоступны для чтения. Интерфейс должен это показывать
честно, а сервер — не предлагать таким `serve`.

### Сторона отправителя

- Один файл: `<input type="file">` или drag&drop.
- Папка: `<input webkitdirectory>` либо `DataTransferItem.getAsFileSystemHandle()`
  при перетаскивании (даёт нормальные относительные пути).
- Чтение всегда ленивое, срезами. Объекты `File` живут, пока жива вкладка —
  отсюда предупреждение «не закрывайте вкладку» в UI.

## 8. Протокол

Стиль и структура — как в `Server/network/README.md` у MeetUp, чтобы клиентописателю
было знакомо.

### HTTP

```
POST /api/transfers
  → { "id": "<16 байт b64url>", "owner_token": "<32 байта b64url>" }
  Создаёт пустую сессию в RAM. Живёт 60 секунд, пока не пришёл offer по WS.

GET /api/transfers/<id>
  → { "total": 8421376, "chunk_size": 1048576, "chunks": 9,
      "manifest": "<b64 шифротекст>", "hash_list": "<b64 шифротекст>",
      "nonce_prefix": "<b64>", "mode": "key" | "password",
      "salt": "<b64>",              // только для mode:"password"
      "state": "active" | "delegated",
      "receivers": 2, "uses_left": 3, "expires_in_ms": 71000,
      "require_approval": false }
  Ничего не сжигает. Имени файла тут нет — оно внутри зашифрованного манифеста.

GET /api/transfers/<id>/challenge
  → { "challenge": "<16 байт b64>" }
```

### WebSocket `wss://<host>/wsf`

Текстовые сообщения — JSON-управление, бинарные — чанки. Формат бинарного фрейма:

```
[ op:1 ][ chunk_index:8 BE ][ payload: шифротекст чанка + тег GCM 16 байт ]
op: 1 = CHUNK
```

#### Отправитель → сервер

```jsonc
{ "type": "offer", "id": "...", "owner_token": "...",
  "total": 8421376, "chunk_size": 1048576, "chunks": 9,
  "nonce_prefix": "<b64>", "verifier": "<b64 V>",
  "manifest": "<b64>", "hash_list": "<b64>",
  "mode": "key",
  "policy": { "uses": null, "ttl_ms": 86400000, "require_approval": false,
              "max_concurrent": 8, "leave_open": true,
              "on_owner_leave": "freeze" } }

{ "type": "approve", "receiver": 7, "ok": true }
{ "type": "policy",  "uses": 5, "ttl_ms": 3600000 }   // только пока владелец на связи
{ "type": "revoke" }                                   // убить раздачу немедленно
{ "type": "resume_owner", "id": "...", "owner_token": "..." }  // вернуться к своей раздаче
```

#### Получатель → сервер

```jsonc
{ "type": "hello", "id": "...", "proof": "<b64 HMAC(V, challenge)>", "name": "Гость" }
{ "type": "subscribe_live" }
{ "type": "request", "ranges": [[0,40]], "budget_bytes": 8388608 }

```

#### Сервер → всем

```jsonc
{ "type": "offer_ok" }

{ "type": "need", "ranges": [[816,831]], "budget_bytes": 8388608 }   // отправителю

{ "type": "peers", "receivers": [ { "id":7, "name":"Гость",
      "progress":0.42, "rate_bps":11800000, "role":"leech"|"seed"|"catching" } ] }
{ "type": "stats", "rate_bps": 118000000, "eta_ms": 42000,
      "src": { "window": 0.71, "peers": 0.29, "sender": 0.0 } }

```

#### Коды ошибок

```
need_key            ключ не предъявлен или не сошёлся (использование НЕ списано)
transfer_not_found  нет такой сессии
uses_exhausted      лимит использований исчерпан
expired             вышел TTL
too_many_receivers  превышен max_concurrent
approval_denied     владелец отказал

```

## 9. Стек и структура репозитория

### Решения

| Слой | Выбор | Почему |
|---|---|---|
| Сервер | **C++20 + Qt6** (Core, Network, WebSockets) | Та же культура, что MeetUp: готовый Docker, nginx-прокси с Let's Encrypt, знакомое слоение. `QByteArray` implicitly shared — отдать один чанк в N сокетов не копирует payload, fan-out почти zero-copy. |
| Транспорт | **WebSocket over TLS** в v1 | Уже работает у тебя, TCP/443 меньше страдает от DPI. WebTransport (стал Baseline в марте 2026, покрытие ~91 %) — за абстракцией транспорта, вторым, с автофоллбэком. UDP в России режут сильнее TCP, так что WS остаётся основным. |
| Веб-клиент | **React + WebCrypto**, Service Worker, OPFS, FSA | Как `Server/web/` в MeetUp, без бандлера. |
| Нативный клиент | **Qt6 Quick/QML** | Модуль в Win11Client. |
| Общий код | статическая библиотека `libferry-core` | Чанкование, AEAD, BLAKE3, манифест. Линкуется и в сервер, и в нативный клиент — форматы не разъедутся по определению. |
| Хеш | **BLAKE3** (официальная C-реализация) | Быстрее SHA-256 в разы, SIMD из коробки. |
| База | **нет** | Сознательно. Ни SQLite, ни файлов. |

### Почему не Rust/Go

Соблазн есть — под такую нагрузку они удобнее. Но: второй язык в экосистеме, свой
билд, свой Docker, и всё это ради пет-проекта, где узкое место — канал, а не CPU.
Qt-шный event loop на одном ядре прокачивает несколько гигабит memcpy-ориентированного
трафика; для VPS на 100–1000 Мбит запас десятикратный. Если упрётся — раздачи
раскладываются по `QThread` через `moveToThread`, интерфейс не меняется.

## 10. Что знает сервер (бюджет приватности)

Полезно иметь явный список — он же идёт в README как обещание.

**Видит:**

- случайный id раздачи;
- размер тома, размер чанка, количество чанков;
- `V` (односторонняя производная ключа), `nonce_prefix`, соль пароля;
- шифротекст манифеста и списка хешей — как непрозрачные байты;
- IP-адреса, тайминги, объёмы;
- имя, которое получатель сам ввёл в поле «как вас зовут» (необязательное).

**Не видит:**

- содержимое файлов;
- **имя файла или папки** — оно внутри зашифрованного манифеста;
- количество и структуру файлов внутри тома;
- content-id: `root` тоже зашифрован, поэтому две одинаковые раздачи не
  сопоставляются между собой;
- ключ шифрования — никогда, ни в каком виде.

**Не пишет на диск:** ничего. Ни логов раздач, ни временных файлов, ни базы.

**Анти-абьюз без хранения:** счётчики в RAM — leaky bucket по IP на создание
раздач, потолок одновременных сессий на IP, потолок исходящего на сессию.
Никакой истории, всё обнуляется при перезапуске.

## 11. Экраны и состояния

Для макета. Структура и копирайт заданы, визуальный язык — нет (§12).

### Отправитель

**S1 · Пустой экран.** Дропзона почти во весь вьюпорт. Две точки входа:
«Выбрать файлы» и «Выбрать папку» — папка равноправна, а не спрятана. Под ней
одна строка про суть: сервер ничего не хранит, шифрование на устройстве.

**S2 · Настройка раздачи** (после выбора, до старта). Сводка тома: имя, размер,
для папки — количество файлов и сворачиваемое дерево. Политика:

- одноразовая ссылка / N использований / без лимита;
- срок жизни (1 ч / 24 ч / 7 дней);
- спрашивать меня перед выдачей (тумблер);
- пароль вместо ключа в ссылке (раскрывающийся блок + предупреждение о стойкости);
- **«оставить раздачу работать без меня»** — с честной подписью: *«после вашего
  ухода настройки уже нельзя будет изменить, а раздача проживёт, пока кто-то,
  скачавший целиком, остаётся на связи»*.

**S3 · Активная раздача.** Главный экран продукта, сверху вниз:

- карточка тома: имя, размер, для папки — количество файлов;
- ссылка крупно, моноширинным, кнопка «Копировать», QR;
- **веер** — центральный визуальный образ: слева том, одна толстая стрела в узел
  «сервер», от узла N тонких к получателям. Подпись: «вы отдаёте один раз».
  Это то, что объясняет продукт за секунду;
- **карта тома** — горизонтальная дорожка на всю ширину, сегментами по чанкам;
  поверх маркеры-курсоры получателей. Догоняющий виден как маркер, который идёт
  второй волной по левой части, пока остальные едут справа. Самый информативный
  элемент интерфейса — на нём видно, что late join работает;
- список получателей: строка на каждого — имя, прогресс, скорость, ETA, чип роли:
  `качает` / `догоняет` / `раздаёт другим` / `готово`;
- строка политики: «осталось 3 использования · истекает через 71 мин» + кнопка
  «продлить»;
- «Закрыть доступ» (деструктивная).

**S4 · Запрос доступа** (модалка, если включено подтверждение). Кто просится (имя
и, если хочешь показывать, укрупнённый регион по IP), кнопки «Пустить» /
«Отказать», галочка «пускать всех дальше».

**S5 · Уход владельца.** Перехват закрытия вкладки. Два варианта текста в
зависимости от `leave_open`: либо «раздача остановится, 2 человека не докачают»,
либо «раздача продолжится без вас; вернуть управление можно по этой ссылке» +
ссылка с owner-токеном и кнопка «Скопировать».

### Получатель

**R1 · Превью.** Что за том (имя из расшифрованного манифеста — значит расшифровка
происходит до показа), размер, для папки — дерево. Состояние раздачи: активна /
работает без отправителя. Кнопка «Скачать». Варианты: поле пароля; «ждём
разрешения»; «отправитель не в сети».

**R2 · Куда сохранить.** На пути A — выбор папки/файла системным диалогом. На
путях B/C — предупреждение о месте: «нужно 12 ГБ свободного места (6 ГБ временно
+ 6 ГБ итог)», и если не влезает — переключение в последовательный режим с
пояснением, что раздавать другим не получится.

**R3 · Загрузка.** Прогресс, скорость, ETA. Отдельно — **две волны**: две полосы
или одна дорожка с двумя цветами, «хвост» и «начало», чтобы человек видел, что
это не сломанный прогресс, а так задумано. Источники тремя микро-индикаторами:
«из буфера · от других · от отправителя» с процентами. Плашка «не закрывайте
вкладку».

**R4 · Обрыв и возобновление.** «Соединение потеряно, 42 % сохранено, продолжим
автоматически» + ручная кнопка. Важно: показать, что прогресс не потерян.

**R5 · Готово.** Галочка, строка «Проверено BLAKE3 — целостность подтверждена»,
путь/кнопка «Открыть папку». Если получатель может сидировать — тумблер «остаться
и помогать раздавать» с пояснением, что это ускоряет остальных.

### Общее

**E · Ошибки** — отдельный макет на каждый код из §8: `need_key`, `uses_exhausted`,
`expired`, `sender_gone`, `too_many_receivers`, `chunk_mismatch`, `no_space`,
`server_busy`. У каждой — что произошло, что делать дальше, и не выглядит ли это
как вина пользователя.

**M · Встроенный режим в MeetUp.** Скрепка рядом с чатом конференции → том
раздаётся участникам комнаты тем же механизмом, в ленте появляется карточка со
счётчиком «скачали 3 из 5». Код тот же, обёртка другая. Проектировать с самого
начала как отдельный React-компонент без глобального состояния, чтобы он
переносился в MeetUp целиком.

## 12. Требования к дизайн-системе

Палитру и типографику выбираешь отдельно. Вот функциональные требования, которые
дизайн-система обязана закрыть — с ними имеет смысл идти в Claude Design.

**Обязательно:**

- **Тёмная и светлая темы равноправны.** Получатель часто открывает ссылку с
  телефона днём на улице.
- **Кириллица во всех начертаниях**, включая моноширинное.
- **Моноширинный шрифт как полноценный элемент системы** — им набираются
  идентификаторы, скорости, размеры, отрезки хешей. Его должно быть не стыдно
  показывать крупно.
- **Шкала состояний чанка**: минимум 5 различимых состояний на карте тома —
  «нет» / «есть» / «в пути» / «пришло от пира» / «пришло от отправителя». Они
  должны читаться **и в оттенках серого** (карта тома — это плотные полоски по
  2–4 px, цветовой слепоты там не прощают).
- **Семантика статусов**: активно / ожидает / предупреждение / ошибка / успех.
- **Плотный режим**: список получателей и дерево файлов на 100+ строк не должны
  превращаться в километровую простыню.
- **Мобильная раскладка обязательна** для всех экранов получателя.
- **QR на светлом квадрате** независимо от темы (иначе не сканируется).

**Чего избегать** (то, что делает интерфейс «сгенерированным»):

- чёрно-лаймовая пара (занята MeetUp и стала штампом);
- неоновые свечения, `box-shadow` с цветным ореолом;
- градиентные заливки кнопок;
- глассморфизм, размытые полупрозрачные панели;
- крупные скруглённые «карточки-таблетки» на всё;
- иконки-эмодзи вместо иконок.

**Тон.** Ferry — инструмент, а не сервис. Ближе к судовой накладной, приборной
панели или почтовой квитанции, чем к лендингу SaaS. Продукт обещает
предсказуемость и отсутствие следов — интерфейс должен выглядеть так же: спокойно,
плотно, с большим количеством точных чисел и малым количеством украшений.

## 13. План по фазам

### Фаза 0 · Скелет (макет)

Статический React-прототип на фейковых данных: все экраны §11, все состояния
переключаются руками. Ничего не шифруется, ничего не передаётся. **Это то, что
делается первым и по этому документу.**

Выход: кликабельный прототип, по которому видно, что продукт понятен без
объяснений.

### Фаза 1 · Один отправитель, один получатель

- `libferry-core`: чанкование, AES-GCM, BLAKE3, манифест для одиночного файла.
- Сервер: `TransferRegistry`, `TransferSession`, `RingWindow`, WS `offer`/`hello`/
  `need`/CHUNK. Без backfill и без политики.
- Веб: отправка файла, приём на путь A (Chrome) и путь C (последовательный поток
  через Service Worker).
- Проверка целостности на приёме.

Выход: файл на 5 ГБ приезжает целым из Chrome в Firefox.

### Фаза 2 · Fan-out и две волны

- Несколько получателей, курсоры, drop-behind, backpressure.
- OPFS-путь B, битовая карта, возобновление после обрыва.
- Backfill: `request`/`have`/`serve`, reflected backfill между получателями,
  коалесцирование, эвристика «последовательный догон vs две волны».
- Карта тома в UI.

Выход: трое качают, третий подключается на 60 %, у первых двух скорость не
меняется. **Это защита ключевого тезиса — момент, ради которого проект.**

### Фаза 3 · Политика и делегирование

- `verifier` и challenge-response, счётчик использований, TTL, `max_concurrent`.
- Подтверждение доступа, `owner_token`, возврат владельца.
- `leave_open` + `on_owner_leave`, состояние DELEGATED.
- Парольный режим (Argon2id) с предупреждениями в UI.
- Анти-абьюз: лимиты по IP в RAM.

Выход: отправитель закрыл вкладку, раздача живёт на сиде, счётчик использований
по-прежнему верен, ссылка гаснет по исчерпании.

### Фаза 4 · Папки

- Манифест-дерево, том как конкатенация, санитизация путей.
- Отправка папки (`webkitdirectory` + drag&drop с `FileSystemHandle`).
- Приём: дерево через `showDirectoryPicker()`, ZIP store/zip64 на остальных путях.
- Дерево файлов в UI на обеих сторонах.

Выход: папка на 40 000 файлов приезжает деревом в Chrome и архивом в Safari.

### Фаза 5 · Нативный клиент и интеграция

- Qt6 Quick модуль, `libferry-core` линкуется напрямую, произвольный доступ к
  файлам без всяких OPFS.
- Встраивание в MeetUp: скрепка в конференции, карточка в чате.

### Фаза 6 · Опционально

- WebTransport вторым транспортом с автофоллбэком.
- Bao/BLAKE3-дерево вместо плоского списка, если понадобятся терабайтные тома.
- Прямые WebRTC-каналы между пирами — **только** если станет ясно, что трафик
  сервера реально мешает; это добавляет ICE/TURN и ломает простоту §2.

## 14. Риски и открытые вопросы

| Риск | Оценка | Что делать |
|---|---|---|
| **Ссылка = ключ.** Кто получил URL, получил файл. | Высокий, системный | Одноразовые ссылки и подтверждение — в v1, а не «на потом». В UI объяснять прямо: ссылка — это и есть ключ. |
| **Service Worker + потоковая отдача в Safari.** | Высокий | Проверить на живом iOS **до** фазы 1. Если не работает — на Safari остаётся путь через Blob с ограничением по размеру, и это надо знать заранее. |
| **Место под OPFS.** 20 ГБ тома = 40 ГБ на диске на пути B. | Средний | `navigator.storage.estimate()` до старта, честное предупреждение, автопереключение на путь C. |
| **Вкладка отправителя.** Закрыл — на v1 конец. | Средний | `beforeunload`, крупный статус «раздача идёт, пока открыта эта вкладка», делегирование в фазе 3. |
| **Память сервера.** Окна съедают RAM. | Средний | Глобальный потолок, динамическое ужимание окна, `server_busy` вместо свопа. |
| **Абьюз.** Релей без хранения всё равно можно завалить трафиком. | Средний | Лимиты по IP в RAM, потолок исходящего на раздачу, `max_concurrent`. |
| **Парольный режим слабее ключевого.** | Средний | Argon2id с честными параметрами, минимум 5 слов, предупреждение в интерфейсе, не делать режимом по умолчанию. |
| **Мобильные браузеры убивают фоновые вкладки.** | Средний | Предупреждение; для длинных загрузок рекомендовать десктоп; в нативном клиенте проблемы нет. |

### Открытые вопросы, которые стоит закрыть до фазы 2

1. **Показывать ли состав получателей друг другу?** Сейчас в §8 сервер шлёт
   `peers` только владельцу. Получателям видеть друг друга незачем, а для
   анонимности лучше не видеть. Оставляем так?
2. **Имя получателя** — оставить необязательным полем или выкинуть совсем? Оно
   единственное, что вообще похоже на идентификацию.
3. **Потолок на повторное чтение у отправителя** — 30 % это догадка. Подобрать
   на реальном тесте с тремя клиентами.
4. **Что делать, если сид отвалился посреди `serve`.** Простой ответ: сервер
   перезапрашивает диапазон у следующего источника, получатель ничего не замечает.
   Проверить, что это не даёт бесконечного цикла при одном флапающем сиде —
   нужен счётчик неудач на источник.

## 15. Бриф для Claude Code: что собирать в макете

Одним абзацем, чтобы можно было скопировать в задачу.

**Собрать статический React-прототип Ferry без бэкенда.** Все данные — фейковые,
все состояния переключаются вручную через панель отладки (выпадающий список
сценария). Ни сети, ни шифрования, ни файлов — только интерфейс.

**Экраны:** S1 пустой, S2 настройка раздачи, S3 активная раздача, S4 запрос
доступа, S5 уход владельца, R1 превью, R2 выбор места, R3 загрузка, R4 обрыв,
R5 готово, плюс восемь экранов ошибок по кодам из §8.

**Ключевые компоненты, на которые стоит потратить больше всего времени:**

1. `<VolumeMap>` — карта тома: горизонтальная дорожка из сегментов по чанкам, пять
   состояний сегмента, поверх — маркеры-курсоры получателей с именами. Должна
   анимироваться (чанки приходят) и оставаться читаемой на 10 000 сегментов
   (агрегировать в пиксели, а не рисовать DOM-узел на чанк).
2. `<FanDiagram>` — веер «том → сервер → N получателей», толщина стрел
   пропорциональна потоку, одна подпись.
3. `<ReceiverRow>` — строка получателя: имя, прогресс, скорость, ETA, чип роли
   (`качает` / `догоняет` / `раздаёт другим` / `готово`).
4. `<TwoWaveProgress>` — прогресс получателя с двумя волнами (хвост и начало
   разными дорожками) и тремя индикаторами источника.
5. `<FileTree>` — сворачиваемое дерево манифеста, виртуализованное, до 100 000
   записей.

**Фейковые сценарии для панели отладки:**

- «один получатель, всё ровно»;
- «трое, один медленный, отстал и догоняет»;
- «третий подключился на 60 % — видно две волны на карте»;
- «отправитель ушёл, раздача делегирована сиду»;
- «папка на 4 812 файлов»;
- каждая ошибка по отдельности.

**Чего в макете не делать:** реальных вычислений, попыток что-то шифровать,
обращений к сети, Service Worker, OPFS. Всё это приходит в фазе 1.
